# Gateway registration and protocol isolation

> Cross-references to sections elsewhere name their file; see `README.md` for the index.

## Two independent backend-connection trackers — the recurring gotcha

There are two separate places that track a backend server's connection state, and both must be invalidated when a backend goes away or the proxy will keep using dead state:

1. **Discovery pollers** — `dynamic_proxy.FeaturePoller[T]` (`dynamic_proxy/feature_poller.go`) is a generic poll-loop/lifecycle/fingerprint-diff core, instantiated once per feature kind: `ToolPoller` (`tool_poller.go`, `tools/list`), `PromptPoller` (`prompt_poller.go`, `prompts/list`), `ResourcePoller` (`resource_poller.go`, `resources/list`), and `ResourceTemplatePoller` (`resource_template_poller.go`, `resources/templates/list`). Each, on its own `<kind>sPollFrequencySeconds` interval (default 5s, configurable via the combined config file's `discovery` section), opens a brand-new, short-lived connection per backend server, lists that kind's items, diffs the result against a fingerprint of what was last seen, and re-syncs the gateway's registrations on change. No connection is held open between polls. `dynamic_proxy.genericRegistry[T]` (`dynamic_proxy/feature_registry.go`) owns each poller plus the per-server bookkeeping of what's currently registered, and is driven uniformly through the `featureRegistry` interface. `dynamic_proxy.Gateway` (`dynamic_proxy/gateway.go`) holds one `genericRegistry` per kind in a `[]featureRegistry` slice; `Gateway.OnAdded` starts all of them for a server, `Gateway.OnRemoved` stops them and removes their registrations. Adding a fifth kind means adding one more `genericRegistry[T]` instance to that slice — no changes to the poll/reconcile logic itself.
2. **Tool-call routing session** — `sessionMap` (`session_proxies.go`, package `proxyserver`), a thin wrapper over `sessioncache.Cache` (`sessioncache/`), the cache `triggered-tools-runtime`'s platform-server sessions use too. One client session per `(proxy client sessionId, backend server, target)`, used to actually forward a specific client's `tools/call` to the right backend. The gateway serves clients statelessly, so every client shares the `""` session ID: one backend session per server, used by every concurrent call. The target (URL and credentials Secret) is part of the key, so a session is only ever reused for what it was opened to: a call that looked a server up just before its removal can't leave a session cached that the server, re-added at another URL, would reuse.
   - **Connects never block other callers.** Concurrent first calls to a backend share one connect (`pending`), which runs outside the cache's lock on its own context: `sessioncache.ConnectTimeout` (10s), carrying no caller's values. Each caller waits only as long as its own request context (`SessionRetriever` takes it). The connect can't use the caller's context: the session outlives the request and is shared, and the SDK keeps the connect context's values for the session's background requests, so a caller's per-request identity (`relayheaders.WithMinter`) would leak into them. An abandoned connect can take the SDK seconds more to return (it tries to notify the server of the cancellation), so the cache finishes the pending entry as soon as the connect's context ends and closes any session that turns up late. The backend transports also bound the TCP dial and TLS handshake (10s); responses aren't bounded, since a tool call may run long.
   - **Removal.** `closeServerSessions` (`Cache.CloseServer`) aborts connects in progress and bumps a per-server `generation` counter, so a connect that completes after the removal is closed and returned as an error, never cached.
   - **Dead connections.** A cached session is dropped as soon as its connection ends (`dropWhenClosed`, a goroutine per session waiting on `ClientSession.Wait`), so the next call reconnects. The SDK ends a connection for good only on a failure it treats as permanent — chiefly a stateful backend answering "session not found" after a restart, or when a request reaches a backend replica that didn't create the session — not on a transient one (a 503, a refused connection), after which the same session keeps working. The call that hit the failure isn't retried, since it may have reached the backend (a non-idempotent tool would run twice).
   - Tests: `sessioncache_test.go` (a waiter giving up, connect timeout, no caller values on the connect, keying on target, removal aborting a connect); `session_proxies_test.go`'s `TestSessionForConcurrentFirstCalls` (run with `-race`), `TestSessionForServerRemovedWhileConnecting`, `TestSessionRecoversFromDeadConnection`, `TestSessionSurvivesTransientFailure`; `runtime_test.go`'s `TestSessionDroppedWhenConnectionEnds`.

When `discover_mcp_servers.ServerMonitor` detects a server disappeared, `main.go`'s `runProxyServer` must clean up *both*: `gateway.OnRemoved(removed)` and `sessions.closeServerSessions(name)` for each removed server name. If you add a third place that caches a backend connection, it needs the same treatment.

Also note: `sessionMap.closeServerSessions` (`sessioncache.Cache.CloseServer`) must remove its map entry even when the underlying `session.Close()` call errors, and closes sessions only after releasing the lock, since closing is a network call (e.g. the backend process is already dead so the graceful close request gets connection-refused) — otherwise the dead entry is never replaced and reconnection is permanently broken for that server.


## Gateway / tool-prompt-resource-template registration

`dynamic_proxy.Gateway` owns the `*mcp.Server` ("dynamic-gateway") exposed to clients. `NewGateway(getSession, isHiddenTool, toolsPollFrequencySeconds, promptsPollFrequencySeconds, resourcesPollFrequencySeconds, resourceTemplatesPollFrequencySeconds)` builds a `genericRegistry[T]` per kind. `isHiddenTool` (`ToolVisibilityFilter`, may be `nil`) is consulted only by the tool kind's `registerTool` — see "Triggered tools / orchestration" (`orchestration.md`) for why this exists (go-proxy's triggered-tool concept) and why it's an injected predicate rather than `dynamic_proxy` importing `triggered_tools_runtime` directly. Each registry's `reconcile` method (passed directly to its `FeaturePoller[T]` as the change callback) is the shared per-kind reconciliation path — register new/changed items, remove ones no longer present — so it runs both on the poller's initial baseline tick (covering initial discovery) and on every subsequent tick where the polled list differs from what was last seen, letting a backend add/remove items at runtime without the gateway needing rediscovery.

Namespacing differs slightly by kind because of how each item is identified: tools/prompts are namespaced by mutating `Name` to `<serverName>.<name>` (split back apart on the first `.` via `removeFirstComponent`), while resources and resource templates are identified by `URI`/`URITemplate` (not `Name`, which need not be unique per the MCP spec) and are namespaced by mutating that field to `<serverName>:<uri>` (split back apart on the first `:` via `splitNamespacedResourceURI` — a colon rather than a dot, since resource URIs/templates routinely already contain dots, e.g. `file:///a.txt` or `file:///{path}`).

**Reads (`ReadResource`) have a dispatch nuance the other three kinds don't**: per the SDK's `Server.readResource`/`lookupResourceHandler` (`mcp/server.go`), an incoming `resources/read` URI is checked against the exact-URI resource map *first*, and only if no exact match is found does the SDK iterate registered templates checking `ResourceTemplate.Matches(uri)` (RFC 6570, via `github.com/yosida95/uritemplate/v3`) and invoke that template's handler instead — with the same `*mcp.ReadResourceRequest`, so `req.Params.URI` is always the concrete requested URI, never the template pattern. This is why `Gateway.registerResourceTemplate` (`gateway.go`) can't capture a single static "original URI" at registration time the way `registerResource` does (a resource is one URI; a template matches many) — it derives `serverName` once from the template's own namespaced name, but re-derives the concrete URI from `req.Params.URI` on every call. It also means no separate request-authorization branch is needed for template-matched reads in `middleware.go`'s middleware: they arrive as the same `*mcp.ReadResourceRequest`/`isResourceRoleAuthorized` check already used for plain resource reads.

Actual invocation (`CallTool`/`GetPrompt`/`ReadResource`) is routed through the `SessionRetriever` function passed into `dynamic_proxy.NewGateway` via the shared `Gateway.SessionFor` helper (both take the calling request's context, only to bound the wait) — in `main.go` this is wired to `sessionMap.sessionFor`, i.e. the second session cache described above, keyed by the *calling client's* session ID.


## Backend protocol version isolation

The same shared `ctx` that carries the internal identity assertion (above) also carries whatever the go-sdk itself stashed on the incoming request — including its own unexported per-request MCP protocol-version tracking. Left alone, that means a client that negotiates the newest protocol version with go-proxy's own (stateless) gateway would cause go-proxy to request that same version against *every* backend it forwards calls to, even one that would otherwise negotiate (and only supports) an older version — and a backend not configured `Stateless: true` rejects the newest protocol outright with a 400. `middleware.go`'s `detachContextValues` fixes this: it's called first thing in `createMiddleware`, before any of go-proxy's own `context.WithValue` calls, and strips the incoming ctx's whole value chain (preserving cancellation/deadline) so only what go-proxy explicitly re-attaches — the internal assertion, the caller's claims — reaches the backend call; the SDK's own context isn't threaded through. Test: `protocol_version_test.go`'s `TestProtocolVersionNotPropagatedToStatefulBackend`, the only test in this repo that points a backend at `Stateless: false` on purpose, to prove a forwarded call still succeeds.

Related, and worth keeping in mind before ever wiring up a `SamplingHandler`/`ElicitationHandler`/`SubscribeHandler` on any of go-proxy's backend-facing clients or its own gateway server: MCP capabilities aren't a static list go-proxy declares, they're derived by the SDK from which handlers are actually registered (see `Client.capabilities`/`Server.capabilities` in the go-sdk). Since none of those handlers are ever set, go-proxy already and automatically tells backends "I don't support sampling/elicitation" and tells its own clients "I don't support resource subscriptions" — both true today, since there's no plumbing to relay a backend-initiated sampling/elicitation request up to the original client (or a subscription's live updates back down). Don't add one of those handlers without also building that relay — doing so would start advertising a capability go-proxy can't actually fulfill.

**Progress relay** (`progress_relay.go`). A client asks for progress with a token in a tool call's `_meta`. The backend's progress notifications arrive on go-proxy's backend session, which all users share, so client tokens can collide. `Gateway.RelayProgress`, called by `registerTool`'s handler and by `proxy_utility.call_tool` for its loopback call, therefore registers a gateway-issued token (`gw-progress-<uuid>`) mapped to the client's `ServerSession`, its original token, and the client request's original context. It sets that token on the forwarded call, and the returned `done` func removes the entry when the call returns. `HandleBackendProgress`, installed as `ProgressNotificationHandler` on the backend clients (`session_proxies.go` via the `backendProgressHandler` package var set in `runProxyServerOn`, and call_tool's loopback client), looks the token up and calls `NotifyProgress` with the client's own token. It uses the *original* context because the stateless handler routes a notification to a request's stream by the SDK's request ID on that context (`idContextKey`, read in `streamable.go`), and `detachContextValues` strips it. So `createMiddleware` saves the original with `WithClientRequestContext` before detaching, and it's used only for this, never for backend calls. Delivery is on the call's own response stream, so it works for every protocol version. Unknown or finished tokens are dropped. Backend *log* messages aren't relayed: MCP is deprecating logging (SEP-2577), backends only send them after a client sets a level, and on a shared session they can't always be attributed to one user. Tests: `progress_relay_test.go` (relay under the client's token, two clients with the same token over one shared backend session, no token → no relay, no leftover entries). For a tool whose orchestration has result checks, `createMiddleware` marks the call `dynamic_proxy.WithoutProgressMessages`, and the relay drops each notification's `message` (free text from the backend no result check sees) while still relaying its progress values. Test: `progress_relay_test.go`'s `TestProgressWithoutMessages`.

**Elicitation pass-through (multi round-trip, SEP-2322).** With protocol 2026-07-28 a backend tool asks for user input by returning a `CallToolResult` with `resultType: "input_required"`, `InputRequests` and an opaque `RequestState`. The client answers and calls the tool again with `InputResponses` and the same `RequestState`. go-proxy only passes this through:
- Its backend clients (`session_proxies.go`, and `proxy_utility.call_tool`'s loopback client) set `MultiRoundTrip: &mcp.MultiRoundTripOptions{Disabled: true}`. Otherwise the SDK client would try to answer the input requests itself, and fail with "client does not support elicitation".
- `registerTool`'s handler, and call_tool, copy `InputResponses` and `RequestState` from the client's request onto the forwarded call. The input-required result is returned to the client unchanged.
- `Guard` (`triggered-tools-runtime/orchestrate.go`) runs an input-required result through the orchestration's result checks like any result: its questions and any content alongside them reach the client, so they can carry what a result check is there to stop. If the checks object it's blocked; otherwise it's returned unchanged. Its result audit is skipped: the follow-up call is a full call of its own. Call authorization runs on both rounds. A result check therefore also sees requests for input; write result constraints so such a result passes (e.g. don't require a field only a final result has). Test: `orchestrate_test.go`'s `TestGuardChecksInputRequiredResults`.
- Limits: only tools. The backend must speak 2026-07-28; a stateful Go SDK server negotiates 2025-11-25 and falls back to an old-style server→client `elicitation/create` request, which go-proxy can't relay (its backend clients register no `ElicitationHandler`, so backends see no elicitation capability). A client on an older protocol can't answer an input-required result.
- Tests: `dynamic_proxy/elicitation_test.go` (backend asks, client answers, request state round-trips), `orchestrate_test.go`'s `TestGuardSkipsResultChecksForInputRequired`.

**Client-facing capabilities, list-changed delivery and readiness.** Three related pieces:
- **Explicit capabilities.** The gateway server is built with an explicit `ServerOptions.Capabilities` (`gateway.go`'s `gatewayCapabilities`): tools, prompts and resources, each with `listChanged`, and no logging. The SDK's default derives capabilities from what's registered at the moment a client connects, so an early client — before discovery had registered any prompt — was told there were no prompts for its whole session.
- **List-changed delivery.** `listChanged` is real only for protocol 2026-07-28+ clients, which open a `subscriptions/listen` stream. That's why `createMiddleware` skips `detachContextValues` for that one method: the SDK's listen handler needs its own request ID from the context (otherwise it fails with "subscriptions/listen requires a request ID"), and listen never calls a backend, so there's no protocol version to leak. Older-protocol clients can't be notified: the stateless handler refuses the GET stream (405), so they see changes on reconnect.
- **Readiness.** `/healthz` also waits for the first discovery pass (`discovery_readiness.go`): `ServerMonitor.FirstCheckDone()` plus `Gateway.InitialPollsPending() == 0` (every discovered server's first poll per feature kind *attempted*, success or failure — `FeaturePoller.PendingFirstPolls`), capped by `discoveryReadyTimeout` (30 s), then latched ready. Kubernetes therefore doesn't route clients to a replica that hasn't loaded anything yet.
- **Tests:** `gateway_capabilities_test.go`, `tool_poller_test.go`'s `TestFeaturePollerPendingFirstPolls`, `mcp_server_monitor_test.go`'s `TestMonitorFirstCheckDone`, `discovery_readiness_test.go`.

## Handler panics

The SDK runs request handlers on its own goroutines (`internal/jsonrpc2`'s `handleAsync`) and never recovers, so `net/http`'s per-request recovery doesn't apply: a panic in any handler would kill the whole process, and every user's calls with it. `createMiddleware` recovers around everything it calls and turns a panic into that request's error, logging the stack. Code that reads a backend's result still checks it rather than relying on this (e.g. `find_relevant_tools` checks `_filter_tool`'s content isn't empty). Test: `utility_tools_test.go`'s "an empty _filter_tool result is an error, not a crash".

## Limits on what a backend can send

- **Tool arguments go through byte for byte.** `registerTool` checks they're a JSON object but forwards the client's bytes as-is, never decoded into `map[string]any` and re-encoded: that would round numbers to float64 (`1e-400` → `0`, `9007199254740993` → `9007199254740992`), so a backend could get a value other than the one a guardrail constraint validated. Test: `arguments_test.go`.
- **Lists are capped.** `collectAllPages` refuses a backend listing more than `maxItemsPerServer` (10,000) tools, prompts, resources or templates; that poll fails and what was last registered stays. Test: `pagination_test.go`'s `TestCollectAllPagesCapsItems`.
- **`find_relevant_tools` trusts the AI server only to choose.** Its candidates are what the caller's `tools/list` would show (`listableTools`: role rules and `listedTools`), and it returns only tools that were candidates, as go-proxy itself described them, so whatever answers as `ai-powered-tools` can't add tools or substitute its own descriptions. An empty `_filter_tool` result is an error. `list_triggered_tools` is filtered by role too.
