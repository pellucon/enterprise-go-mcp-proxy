# Discovery and namespace layout

> Cross-references to sections elsewhere name their file; see `README.md` for the index.

## Discovery flow

`discover_mcp_servers` (package): finds backend MCP servers via a JSON config (the combined config file's `discovery` section, see "Commands" (`../../CLAUDE.md`)), in one of three modes:
- `"static"`: server names/URLs listed explicitly in the config file.
- `"scan"`: scans running OS processes (via `github.com/shirou/gopsutil`) for `--mcpServerName=`/`--mcpServerUrl=` command-line flags — this is why manually-run backend MCP servers in this repo are launched with those flags. Scan mode has no pins, and any local user can start a process with any command line, so `checkScanProcess` accepts a process only if it runs as go-proxy's own user (every user ID gopsutil reports for it) and its URL is http(s) on `localhost` or a loopback address; anything else is skipped and logged. Test: `discover_mcp_servers_test.go`'s `TestCheckScanProcess`.
- `"k8s"`: lists k8s Services (via `client-go`, `k8s_discovery.go`) matching `discovery.k8sLabelSelector` (default `mcp.io/role=backend-mcp-server`) in each namespace of `discovery.k8sNamespaces`, and turns each into a `ServerAttributes` pointed at that Service's cluster-DNS name (`http://<svc>.<namespace>.svc.cluster.local:<port>`, port/path overridable per-Service via the `mcp.io/port`/`mcp.io/path` annotations) so kube-proxy load-balances across whatever pods currently back it. This is the mode `proxy-server.cfg`/`go-gardening-demo/gardening-demo.cfg` actually use. Every Service found is trusted as a backend (it receives users' tool calls and identity assertions), so discovery is opt-in per namespace — see "Discovery trust rules" below.

### Discovery trust rules (k8s mode)

`buildServerMap` (`k8s_discovery.go`) is where a listed Service becomes — or doesn't become — a backend. Each rule closes a way a Service owner could otherwise take more than their own backend:
- **Namespaces are an explicit allowlist.** `k8sNamespaces` is required (non-empty) in k8s mode; there is no "whole cluster" setting. RBAC matches: `scripts/deploy.sh`'s `apply_discovery_rbac` applies `k8s/discovery/go-proxy-discovery-rbac.yaml` (a namespaced `Role` + `RoleBinding` for `services: get/list/watch`) into exactly those namespaces, reading them from the live `discovery-override` ConfigMap when it exists (it wins over the cfg). go-proxy has no cluster-wide Service access. A namespace listed in config but missing its Role makes every discovery tick fail (logged by `ServerMonitor`), keeping the last known servers.
- **Credentials come only from config.** `k8sCredentials` maps `"<namespace>/<service>"` — the Service's real identity, never its claimable server name — to a credentials Secret (`backendauth`). No annotation can assign a credential: if one could, any Service could name any Secret in go-proxy's namespace and receive its credentials.
- **The URL is built, not spliced.** `serverUrlFor` assembles a `url.URL` from the Service's own name/namespace; `mcp.io/path` must be a plain absolute path (no `//` prefix, `?`, `#`, `@`, `\` or control characters — `@` would turn the cluster hostname into userinfo and point the URL at any host), `mcp.io/port` must be 1–65535, and `ExternalName` Services are skipped. An invalid Service is skipped and logged, never given a fallback.
- **Names are validated and contested names resolve deterministically.** Server names must match `ValidateServerName` (`^[A-Za-z0-9][A-Za-z0-9_-]*$` — no `.`/`:`, which namespacing splits on), in every discovery mode. When several Services claim a name, the earliest namespace in `k8sNamespaces` wins, then a Service whose own name is the server name, then the lowest Service name; every claimant is logged. `k8sPinnedServers` (`name → "<namespace>/<service>"`) goes further for names the gateway depends on — the shipped cfgs pin `rate-limiter`, `declarative-guardrail`, `event-aggregator` and `ai-powered-tools` to `mcp-proxy` — so no other Service can take them, even while the real one is missing.
- **Names go-proxy trusts for a security decision must be pinned.** Any Service in a listed namespace can claim any unpinned name, and some names decide security outcomes: a squatter on `rate-limiter` or a guardrail server could approve every call, and one on an `internalAuth.relay` source gets relay tokens to call other backends as each user. `proxyserver/pinning.go`'s `trustedServerNames` lists them, each with why: the three platform servers go-proxy calls by a fixed name (`rate-limiter`, `declarative-guardrail`, `ai-powered-tools` — always, configured or not, so enabling a feature later never depends on remembering a pin), every server an orchestration step runs on (including the `guardrailServer`/`aiValidatorServer` a native step's parameters name), and every `internalAuth.relay` source. A guarded tool's own server isn't on the list even though a business-logic step asks it for the verdict: a Service that claimed it would receive the call itself anyway. This is enforced in two places:
  - **Discovery** (`DiscoverMCPsFromConfig`'s `MustPin`, checked in `buildServerMap`) never accepts an unpinned trusted name from any Service; it's skipped and logged, and whatever depends on it fails closed as if its server were unreachable. This covers every path a config can change by, including a direct ConfigMap edit.
  - **Config checks** (`UnpinnedNames`) give the reason up front: startup fails, and `_admin.update_discovery` (dropping a needed pin) and `_admin.update_orchestration` (a step on an unpinned server) are refused, each naming the missing pins and why. To add a step on a new server, update discovery to pin it first. Static mode needs no pins: its names come from the config itself.
  - Tests: `k8s_discovery_test.go`'s `TestBuildServerMapMustPin`, `TestUnpinnedNames`; `pinning_test.go`.
- **Problems are logged once, not every tick.** `buildServerMap` returns its skip/collision messages instead of logging them, and `k8sProblems` (`problem_log.go`'s `problemLog`, also used by scan mode and by `ServerMonitor` for a failed discovery) logs each distinct message when it first appears and again only after it clears and comes back — discovery runs every `frequencySeconds`, so logging directly would repeat a lingering misconfigured Service forever. `ServerMonitor` logs "discovery recovered" once a failing discovery succeeds again.
- **A changed server is replaced, not ignored.** `ServerMonitor` diffs full `ServerAttributes`, so a server whose URL or credentials Secret changes under the same name (a config update, or a different Service winning the name) fires `onRemoved` with the old attributes and then `onAdded` with the new ones — removals always fire first.

`discover_mcp_servers.ServerMonitor.Start` polls on a `frequencySeconds` interval (an immediate baseline check on start, then every tick), diffs the current server map against the last-seen one, and fires `onAdded`/`onRemoved` callbacks with just the delta.

### Namespace layout

Four categories, three of them fixed:
- **`mcp-proxy`** — go-proxy itself and every `platform-mcp-servers/*` backend. Not just organizational: `declarative-guardrail`/`event-aggregator`/`rate-limiter` each mount a `<section>-override` ConfigMap go-proxy's own `configsync.Writer.EnsureSeeded` seeds (see "Configuration sync (configsync)" (`configsync.md`)), and a ConfigMap volume mount only ever works same-namespace. NATS lives here too, reached via the unqualified short DNS name `nats:4222` (works because it's same-namespace with everything that dials it).
- **`gardening-demo`** — every `go-gardening-demo/servers/*` backend.
- **`demo-auth`** — `demo-authorization-server`.
- **Everything else** (`ai-mcp-servers/ai-powered-tools`, or a `--deploy-server PATH` target) — no fixed namespace assumed at all: `scripts/deploy.sh`'s `--namespace` flag decides (default `mcp-proxy`, purely for convenience — nothing else, no NetworkPolicy/RBAC, is tailored to wherever it actually points), and the namespace is created on demand (`kubectl create namespace ... --dry-run=client -o yaml | kubectl apply -f -`) rather than assumed to pre-exist. Whatever namespace that is must also be in `discovery.k8sNamespaces` for go-proxy to discover the backend — `deploy.sh` warns when it isn't — and a server pinned in `k8sPinnedServers` (e.g. `ai-powered-tools`) is only accepted from its pinned namespace.

Every manifest in this repo's `k8s/` directories is namespace-agnostic (no `metadata.namespace` field) — placement is decided solely by `-n <namespace>` at apply time in `scripts/deploy.sh`, which is also what makes `--namespace` actually work. `scripts/cleanup-k8s-cluster.sh` deletes the three fixed namespaces wholesale (never an "other" one — no assumption about where that lives); `scripts/observe-k8s.sh` lists pods across those same three, plus Jobs in `gardening-demo` (today, just `gardening-demo-seed` — see "In-cluster gardening-demo seeding" (`build-deploy.md`)).

NetworkPolicies mirror this split: `k8s/networkpolicy-allow-proxy-to-backends.yaml` (in `mcp-proxy`) uses a same-namespace `podSelector` for "only go-proxy can reach backend pods." `gardening-demo`'s own `go-gardening-demo/k8s/networkpolicy-allow-ingress-from-proxy.yaml` is the cross-namespace equivalent — it combines a `namespaceSelector` (matching `mcp-proxy` via the auto-set `kubernetes.io/metadata.name` label) with the `app: go-proxy` `podSelector` in the same `from` entry (AND semantics) to express the same guarantee across namespaces. An "other"-bucket namespace gets no namespace-wide policy — it may host unrelated workloads, which a default-deny would cut off. Instead `deploy_folder`'s `isolate_backend` (`scripts/lib/deploy-servers.sh`) gives each backend Deployment it deploys there an `allow-only-go-proxy-to-<deployment>` policy selecting just that Deployment's pods (its own selector): selecting them isolates them, and the policy admits only go-proxy. A discovery namespace with no NetworkPolicy at all gets a warning at deploy time (`warn_if_unprotected`), since its backends may be someone else's to protect.
