# Configuration sync and runtime log level

> Cross-references to sections elsewhere name their file; see `README.md` for the index.

## Configuration sync (configsync)

Every combined-config section except `auth`/`internalAuth`/`roleMapping` (deliberately untouched — `roleMapping` decides who may call the admin tools, so those tools must never be able to change it; see "Auth and access control" (`auth.md`)) is **live-updatable, admin-tool-exportable/importable, and cross-replica/cross-restart durable** via a shared package, `configsync` (`configsync/`, import path `github.com/pellucon/enterprise-go-mcp-proxy/configsync`), covering `accessRules`, `orchestration`, `discovery`, `eventDictionary`, `declarativeGuardrails`, `eventAggregation` (event-aggregator's ingestion filter and tiered-storage thresholds — see "NATS event system" (`events.md`)), `rateLimiting` (see "Rate limiting" (`rate-limiting.md`)), and `logLevel` (see "Runtime log level") — 8 sections in total.

- **The k8s object**: one `"<section>-override"` ConfigMap per section, go-proxy the sole writer, one JSON data key (`config.json`) holding a `configsync.VersionedConfig[T]{Version, Config}` envelope. `Version` starts at 0 (never written) until go-proxy itself seeds it to version 1 from its own parsed `proxy-server.cfg`, the moment it starts — `configsync.Writer[T].Reconcile` (`configsync/writer.go`), called once per section with that section's own parser from `main.go`'s `doRunOn` right after all 8 `Writer`s are constructed, before the HTTP listener (and therefore `/healthz`) ever comes up. A `Create` racing another replica's (`apierrors.IsAlreadyExists`) is treated as success, the same get-or-create idiom `internal_signing_key.go`'s `bootstrapInternalSigningKey` uses for its own Secret. `scripts/deploy.sh` has no seeding step; its bounded `kubectl rollout status deployment/go-proxy` wait in `deploy_proxy` guarantees every section is seeded before any dependent platform-server pod starts, and on failure prints the new pod's log.
- **Once seeded, the override is the live config and the cfg never overrides it — so a cfg that contradicts it is refused (`Reconcile`).** Otherwise an edit or revocation made in the cfg would silently do nothing. Each ConfigMap has a second data key, `cfg-hash` (`cfgHashKey`): the baseline, a sha256 of the cfg section the live config last agreed with, written by the seed. `Update` rewrites only `config.json`, so admin updates carry the baseline over. At startup, with both values normalized through the section's parser and re-encoded (so defaults the parser fills in, or key order, never count as a difference; admin updates store their input unparsed):
  - **cfg hash == baseline** — the cfg is untouched and the live config moved on through admin updates (the normal way to change config): start, logging a warning that the cfg is behind. Restarts between an admin update and regenerating the cfg must work, so this can't be refused.
  - **cfg hash != baseline, cfg == live** — a cfg regenerated with `export_full_config`: start, and record it as the new baseline (otherwise the next admin update plus restart would look like a contradicting edit).
  - **cfg hash != baseline, cfg != live** — the cfg was edited since: `*configsync.DriftError`. `doRunOn` collects them across sections and fails with `config_drift.go`'s `driftError`, a one-line message (slog escapes newlines) naming the cfg keys, the CLI `update-…` commands, `export-full-config`, and the `<section>-override` ConfigMaps to delete to let the cfg win instead.
  - A section absent from the cfg counts as an empty value: removing a seeded section from the cfg is a contradicting edit too. An override without a baseline adopts the deployed cfg as its baseline. A failed baseline write is only logged.
  - Tests: `writer_test.go`'s `TestReconcileK8s_*`, `TestUpdateK8s_KeepsBaseline`; `config_drift_test.go`.
- **`configsync.Writer[T]`** (proxy admin-tool handlers only): `Update(ctx, VersionedConfig[T])` does a fresh k8s GET of the ConfigMap, rejects if the caller's `Version` doesn't match the map's actual current version (optimistic concurrency — the k8s `resourceVersion` from that same GET also makes a racing concurrent writer's own `Update` call fail outright), otherwise writes `{Version: current+1, Config}` and pings `_system.config.<section>` on NATS (bare, payload-less — a subscriber always reacts by re-reading its own file, never by trusting the message). `Export(ctx)` reads the ConfigMap's current value the same way. Outside k8s, both fall back to an in-process value (still seeded from `proxy-server.cfg` at version 1, still version-checked, just not cross-replica) — this is real, supported standalone-binary behavior, not a test stub.
- **`configsync.Watcher[T]`** (every reader: go-proxy's own engines, and every backend server consuming `eventDictionary`/`declarativeGuardrails`/`logLevel`): reads+parses+validates a local mounted file once at construction (fail-closed on a malformed file; falls back to a caller-supplied `initial` value if the file doesn't exist yet), and — if a NATS connection was given — reloads that same file on every ping, with bounded retry/backoff (kubelet's ConfigMap→volume sync isn't instant) that gives up and keeps the last-good value if the new content never lands within `configsync.ReloadTimeout`. Pings are only the fast path: whenever it's subscribed (non-nil NATS connection and a non-empty path), each Watcher also re-checks its file every `configsync.PollInterval` (30 s; a var so tests can shorten it), applying it if the bytes changed and logging that the update was "picked up by the periodic re-check". That safety net exists because a ping-driven reload stops at the *first* change it sees: on a fresh deploy the kubelet can deliver its stale cached version first (a pod that started before its ConfigMap existed got v1 while the seed Job's ping was for v2), or the file can sync after `ReloadTimeout`, or a ping can be lost on a NATS reconnect — before the poller, any of those left the Watcher stale until some unrelated later ping (observed: go-proxy enforcing seed-time access rules v1 instead of v2). The poll goroutine skips a tick while a ping reload holds `reloadMu`, and `Close` waits for it (`pollWG`) so a closed Watcher is fully quiesced. Regression tests: `configsync/watcher_test.go`'s `TestWatcher_StaleAfterPingIsRecoveredByPoll` and friends. `onChange`, an optional constructor callback, fires once at construction and again on every successful reload, so a caller with its own downstream engine (`access_control.AccessPolicyEngine.Update`, `triggered_tools_runtime.Runtime.Update`, go-proxy's own `eventsClient.SetDictionary`, `logging.ApplyConfig`) never special-cases "first load" vs. "reload" — both go through the same call. A section with no separate engine (`discovery`, `rateLimiting`) has the Watcher itself *be* the engine (`ServerMonitor`'s poll-tick callback reads `discoveryWatcher.Current()` directly, `rate_limit_gate.go`'s `checkRateLimit` reads `rateLimitingWatcher.Current()` directly — real enforcement runs inside the separate rate-limiter server, not go-proxy); `Watcher.SetLocal` lets an admin-tool handler apply an update immediately on the replica that served the call, without waiting for its own NATS round trip.
- **`main.go` wiring**: `doRunOn` requires `proxyCfg.NatsURL` to be non-empty (checked explicitly before `configsync.Connect`, which itself silently no-ops on an empty URL) and builds one package-level `natsConn` (`configsync.Connect(proxyCfg.NatsURL)`, independent of `eventsClient`'s own connection — see "NATS event system" (`events.md`)), one `Writer[T]` per section, and a `Watcher[T]` for the 6 the proxy reads back itself (`accessRules`, `orchestration`, `discovery`, `eventDictionary`, `rateLimiting`, `logLevel`), each Watcher's file path derived via `overrideMountPath(configPath, section)` = a sibling directory of `configPath` itself (e.g. `configPath` `/etc/proxy-server/proxy-server.cfg` ⇒ `/etc/proxy-server/access-rules-override/config.json`) — no separate flag/config field needed, and a hermetic test pointing `configPath` at a `t.TempDir()` gets a writable, sandboxed override path for free. `k8s/go-proxy-deployment.yaml` mounts exactly those 6 ConfigMaps at exactly those sibling paths (optional, so a manual/partial deploy — before go-proxy's own `EnsureSeeded` has ever run against this cluster — still starts cleanly). The `eventDictionary` Watcher's `onChange` is `eventsClient.SetDictionary`; see "NATS event system" (`events.md`) for why go-proxy needs its own dictionary at all (it's a publisher, not just an admin surface). The `logLevel` Watcher's `onChange` is `logging.ApplyConfig` directly — see "Runtime log level". `declarativeGuardrails` and `eventAggregation` each still get a `Writer` but no `Watcher` — go-proxy is their sole admin surface but never itself a consumer (their real consumers, `declarative-guardrail` and `event-aggregator`, each run their own separate `configsync.Watcher` against the same mounted ConfigMap).
- **`admin_tools.go`**: `registerAdminTools` is an 8-line table over one generic `registerSectionAdminTools[T]` (mirroring `dynamic_proxy.Gateway`'s one-`genericRegistry[T]`-per-kind idiom) — `_admin.update_<section>`/`_admin.export_<section>` for all 8 sections (except `discovery`, which needs its own dedicated `registerDiscoveryAdminTools` instead — see its own doc comment for why), all exchanging a `configsync.VersionedConfig[T]` envelope, not a bare config struct. **An update is validated before anything is written**: `update_<section>` re-encodes the config and runs the parser that section is loaded with (`validateWith(access_control.ParseConfig)`, `triggered_tools_runtime.ParseConfig`, `events.ParseDictionary`, `guardrailcfg.ParseConfig`, `events.ParseAggregationConfig`, `ratelimit.ParseConfig`, `logging.ParseConfig`; discovery's own tool does the same with `discover_mcp_servers.ParseConfig`), refusing with "invalid …, not applied" — so an admin update can't hand `apply` a config the section's own loader would reject, nor leave an override every replica fails to start with (test: `configmap_test.go`'s `TestAdminUpdatesAreValidated`). `update_<section>`'s `apply` parameter (the engine-specific `onChange`-equivalent) runs synchronously right after a successful `Writer.Update`, so the replica that served the admin call reflects it immediately, independent of the NATS round trip every *other* replica's own `Watcher` relies on. `event_dictionary`'s `apply` is `eventsClient.SetDictionary` directly — `natsUrl` being mandatory means `eventsClient` is never nil here. `rate_limiting`'s `apply` is `rateLimitingWatcher.SetLocal` — no separate engine object, same as `discovery`. `log_level`'s `apply` is `logging.ApplyConfig` directly — the package-level `slog.LevelVar` itself is the engine. `declarative_guardrails`' and `event_aggregation`'s `apply` are both `noApply` — the "no downstream engine to notify" stand-in, since go-proxy never consumes either section itself. Together with `export_full_config` below, this is 17 native admin tools in total (8 sections × 2, plus one).
- **Confirming a backend loaded an update (`guardrail_confirm.go`)**: a section a *separate backend* consumes reaches it only through the kubelet's ConfigMap-to-volume sync, which lags `Writer.Update` by up to a couple of minutes — while the proxy applies its own sections instantly. For `declarativeGuardrails` that lag broke a common sequence: add a declaration, then an orchestration step naming it (exactly what `go-gardening-demo`'s `cli init` seeding does) — the step ran immediately, `evaluate_declarations` answered "unknown declaration", and every call through it failed closed until the kubelet caught up. So `registerSectionAdminTools` takes an optional `confirm(ctx, version) string`, run after `apply`, and `update_declarative_guardrails` passes `confirmDeclarativeGuardrailsLoaded`: it polls the guardrail server's `get_config_version` tool (backed by `Watcher[T].Version()`, the envelope version of the file the Watcher last applied; 0 on the initial fallback, unchanged by `SetLocal`) every `guardrailConfirmInterval` (2 s) until it reports the written version or later, up to `guardrailConfirmTimeout` (3 min). It never fails the admin call (the write already happened) — it appends "Confirmed in effect…", a timeout WARNING, or "Not confirmed…" (unreachable server, or one without `get_config_version`, which fails fast with no retry) to the result text. Skipped outside k8s, where `Writer.Update` never touches the backend's file so the wait could never succeed. Limitation: with several declarative-guardrail replicas only the one this proxy's session reaches is checked. Tests: `guardrail_confirm_test.go` (the wait loop, with an injected fetch), `watcher_test.go`'s `TestWatcher_VersionTracksTheLoadedOverrideFile`.
- **`_admin.export_full_config`** (`admin_tools.go`'s `registerExportFullConfigTool`) is the one admin tool that isn't a `registerSectionAdminTools` pair — read-only, no matching `update_full_config`, and spans all 8 configsync-managed sections (via each `Writer.Export`, unwrapped down to just `.Config` — deliberately no `VersionedConfig` envelope anywhere in the output, so the result is byte-for-byte a valid `proxy-server.cfg`) plus the 5 sections that are never configsync-managed at all (`auth`/`internalAuth`/`roleMapping`/`selfUrl`/`natsUrl`, retained verbatim in package vars — `authConfig`/`internalAuthConfig`/`roleMappingConfig`/`selfURL`/`natsURLConfig` — purely so this tool can round-trip them, since nothing else in `main.go` ever needed them kept around after startup). Saving its output and deploying with it reproduces a running gateway's exact current configuration, including every admin-tool change made since its own last deploy — every section's version simply resets to 1 on next seed, since versions aren't part of the exported document. Two type-level details make this round-trip work: `triggered_tools_runtime.OrchestrationConfig.MarshalJSON` normalizes a nil `Orchestrations`/`ToolMappings` (Go zero value, e.g. an orchestration section that's never been configured) to `{}`/`[]` rather than `null` — the MCP SDK's output-schema validation rejects a bare `null` against a schema derived from a non-pointer map field. `discover_mcp_servers.MCPDiscoveryConfig` has matching `MarshalJSON`/`UnmarshalJSON` methods that convert to/from the same `discoveryMode`/`servers`/... wire shape `ParseConfig` accepts (delegating to it directly) — without them encoding/json would emit `{"Mode":...,"ServerMap":...}`, which `ParseConfig` doesn't accept. Because `jsonschema.For` (schema-inference for a tool's output) reflects on a struct's raw fields and never invokes `MarshalJSON`, `fullConfigExport.Discovery` is declared `any` rather than `discover_mcp_servers.MCPDiscoveryConfig` directly — same reasoning, and same fix, as `triggered-tools-runtime/contract.go`'s `CallRequest`/`CallResult` fields (an `any` field is schema-unconstrained, but still marshals via the dynamic value's own `MarshalJSON`, exactly as if it were statically typed).
- **Backend-side wiring**: `declarative-guardrail`'s parsing/compiling/role-expression logic lives in an importable `platform-mcp-servers/declarative-guardrail/guardrailcfg` subpackage (go-proxy, itself `package main`, can't import another `package main`) — `main.go` builds a `configsync.Watcher[guardrailcfg.Guardrails]`, and its tool handler reads `Current()` per call. `events.Dictionary.validateShape` (invoked from `ParseDictionary`) rejects an unsupported `MetadataFieldSpec.Type` at load time. `events.Client.dictionary` is mutex-guarded via `SetDictionary` — `event-aggregator` wires a `configsync.Watcher[events.Dictionary]` (`onChange = eventsClient.SetDictionary`) alongside its existing `events.Client`, reusing the same `-nats-url` it already had for event pub/sub. Both `guardrails_test.json` (declarative-guardrail's local-dev/test default) and root `proxyserver/testdata/event_dictionary_test.json` are `{"version":1,"config":{...}}` envelopes, matching what a mounted override ConfigMap holds — the same file-reading code path serves the initial load and every later reload, no special-casing.
- **Test**: `configmap_test.go` (`proxyserver` package) drives the real end-to-end admin-tool-call path — an `_admin.update_role_permissions` call, observed by a second, independent `Watcher` standing in for a second replica (same NATS subject, same override path a real k8s deployment would mount that replica's own Watcher at) — plus a version-mismatch case (a stale second update is rejected without changing anything) and a same-replica sanity check. `configsync`'s own `writer_test.go`/`watcher_test.go` cover the k8s-ConfigMap half (via `k8s.io/client-go/kubernetes/fake`) and the file/NATS-reload half in isolation — `configsync.getK8sClientset` is an unexported `sync.Once` singleton with no injection seam from another package, so a real end-to-end test against a fake clientset isn't possible from the root package.


## Runtime log level

`logging` (`logging/`, import path `github.com/pellucon/enterprise-go-mcp-proxy/logging`) is the one logging API and one
runtime-adjustable severity threshold shared by every server in this module — go-proxy itself,
every `platform-mcp-servers/*`/`ai-mcp-servers/*`/`go-gardening-demo/servers/*` backend,
`demo-authorization-server`, and `claude-bridge`. Nothing in the module logs through stdlib `log`,
`log/slog` or bare `fmt.Printf` directly.

- Four severities (`Error`/`Warning`/`Info`/`Debug`, `Info` currently unused — nothing is yet
  classified at that level), but the configurable threshold is only ever `"error"`/`"info"`/
  `"debug"` — `Warning` has no dedicated setting of its own, visible whenever the level is
  `"info"` or `"debug"`, suppressed at `"error"`.
- The threshold lives in a package-level `*slog.LevelVar`, which `slog.HandlerOptions.Level`
  accepts as a live `Leveler` rather than a fixed value — the handler calls `.Level()` on *every*
  log call, so `Init`/`SetLevel` take effect immediately, on the very next call, in every goroutine,
  with no logger reconstruction and no restart. Safe to call from any goroutine (an HTTP handler, a
  `configsync` NATS-reload callback, `main`'s own startup path) with no extra locking, since
  `slog.LevelVar` is itself `atomic.Int64`-backed. `Init` falls back to `"info"` for an unrecognized
  level string and logs that fallback at `Error` — so a typo'd override is visible rather than
  silently swallowed.
- **Config**: an optional `logLevel` combined-config section (`logging.LevelConfig{Level string}`),
  applied once at the very start of `doRunOn` (before NATS/writers/watchers are even constructed,
  so early startup logging already honors it) and thereafter live-updatable the same `configsync`
  way as every other section — `logging.ApplyConfig` (the `func(*LevelConfig)` shared, by
  convention, between `configsync.NewWatcher`'s `onChange` and `registerSectionAdminTools`'
  `apply`, the same "one function reused for both" shape `eventsClient.SetDictionary` already
  follows for `eventDictionary`) is itself the downstream engine — there's no separate object to
  notify. A `nil`/empty-`Level` config is a no-op, keeping whatever level the process already has.
- **Every other server in the module follows the identical pattern independently** — e.g.
  `rate-limiter`'s own `-log-level-config` flag builds a second `configsync.Watcher[logging.
  LevelConfig]`, live-reloaded over the *same* NATS connection it already holds for its own
  `rateLimiting` config, so `_admin.update_log_level` takes effect on every replica of every
  server, not just go-proxy, once each has processed the resulting NATS ping. Unlike a server's own
  primary config file, a missing/not-yet-seeded `log-level-override` mount is deliberately
  non-fatal everywhere — it just leaves the process at its `"info"` default.
