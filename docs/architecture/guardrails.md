# Declarative and business-logic constraint validation

> Cross-references to sections elsewhere name their file; see `README.md` for the index.

## Declarative constraint validation

`platform-mcp-servers/declarative-guardrail` exposes one ordinary (non-triggered) tool, `evaluate_declarations`: given a caller's roles and a list of configured declaration names, it returns one `guardrailcfg.ActionResult` per declaration that both matches its role expression (`RoleExpression`, a small boolean grammar over role names — see `guardrailcfg/roleexpr.go`) and falls within its optional effective-date/time window. `ActionResult{Roles, DeclarationName, Constraint, Actions}` — `Constraint` (`guardrailcfg/evaluate.go`) is the restriction text a caller should validate its actual input/result against; an empty `Constraint` is a convention meaning every input/result violates it, no validation needed. `Actions` (plain strings — `"block"`/`"alert"`/`"log"`, validated against a config-wide catalog at load time, no Go constants) is copied through verbatim; `guardrailcfg`/`evaluate_declarations` never interpret or dispatch them — that's entirely up to the caller.

- **`constraints_validation.go`** (`proxyserver` package) is that caller: `constraintsValidation(ctx, sess, target, roles, declarationNames)` calls `evaluate_declarations` on `sess`, then for every returned `ActionResult` decides whether it "triggered" — an empty `Constraint` always triggers; a non-empty one is compiled as a JSON Schema fragment via `github.com/santhosh-tekuri/jsonschema/v6` and `target` is validated against it, where a `*jsonschema.ValidationError` (target violates the schema) means triggered. `format` (email, uri, date-time, …) is enforced (`compiler.AssertFormat()`). External `$ref`s aren't loaded (`compiler.UseLoader(jsonschema.SchemeURLLoader{})`): the default loader reads `file://` URLs, which would let a constraint make go-proxy read local files. A `Constraint` that fails to compile, or any other validate error, makes that declaration "could not be checked" — triggered, see "Fail closed, per declaration" below — never aborting evaluation of the rest ("try all of them even if one of them failed"); only a failure to call `evaluate_declarations` itself is a hard error - including an answer without `results` (no structured content, or the key missing), which would otherwise read as "no declaration triggered" and let every call through (`TestConstraintsValidation_NoResultsFailsClosed`).
- **Result guardrails cover tool results only.** `resultAuthorization` runs on `tools/call` results (including input-required ones, see `gateway.md`), and a result-checked tool's progress messages are dropped. `prompts/get` and `resources/read` are never orchestrated: data a result check protects on a tool must not also be reachable through a prompt or resource of the same server. `github.com/google/jsonschema-go` (used elsewhere in this repo for Go-struct-derived schema generation and property-name-set comparison, see `validate.go` below) never validates an arbitrary JSON value against a schema, which is why this is a separate dependency.
- **`proxy_utility.request_constraints_validation`/`proxy_utility.result_constraints_validation`** are the two native triggered tools (see "Native (in-process) triggered tools" (`orchestration.md`)) built on `constraintsValidation`: they decode `declarationNames`/an optional `guardrailServer` override (default `"declarative-guardrail"`) from the step's `Parameters`, call `constraintsValidation` with `target = in.CallRequest`/`in.CallResult` (the *whole* marshaled `*mcp.CallToolParamsRaw`/`*mcp.CallToolResult` — a constraint validating "the request parameters"/"the result" must nest under `"arguments"`/`"structuredContent"` accordingly, not assume a bare payload), and for every triggered `ActionResult`'s `Actions`, independently: `"block"` publishes an `alert`/`tool-call-blocked` (request) or `alert`/`result-blocked` (result) event **and** contributes to the returned `Authorized: false`; `"alert"` publishes `alert`/`tool-call-alert`/`result-alert` (independent of `"block"` — a single triggered `ActionResult` naming both publishes two separate events); `"log"` just logs. The `authorization-mcp-server` stand-in's `publishAlert` shape (`dispatchConstraintActions`/`publishConstraintAlert` mirror it exactly, reusing go-proxy's own package-level `eventsClient`) — see `proxyserver/testdata/orchestration_test.cfg`'s `"declarative-constraint-guardrails"` orchestration for a worked example wiring these two tools as `callAuthorization`/`resultAuthorization` steps alongside a JSON-Schema-shaped declaration.
- **`tool-call-blocked`/`result-blocked`** are also the subtypes the `authorization-mcp-server` stand-in's `publishAlert` uses for its rejections — this groups every "this call/result was blocked" alert under one consistent name regardless of which mechanism (fixed rule vs. declarative constraint) produced it, while `tool-call-alert`/`result-alert` are new, reserved for the declarative `"alert"` action specifically (never fired by that stand-in, which has no concept of "alert without blocking").
- **`proxy_utility.request_ai_constraints_validation`/`result_ai_constraints_validation`** are the native triggered tools for a `Constraint` that isn't expressible as a JSON Schema fragment at all (e.g. "must not disclose a customer's SSN") — `guardrailcfg.RawDeclaration.Constraint`'s own doc comment anticipates this: "free-form text for an LLM-based [validator]". They share `evaluate_declarations`'s declaration lookup (`evaluateDeclarations`) and `dispatchConstraintActions`/`publishConstraintAlert` with the JSON-Schema path — only the "did this `ActionResult` trigger" decision differs: `aiConstraintsValidation` calls `ai_result_validator` (`ai-mcp-servers/ai-powered-tools`, alongside `_filter_tool`, sharing that server's completion backend — real LLM API key or headless-Claude bridge, see "AI-powered tool discovery" (`utility-and-ai-tools.md`)) with `{callResult, constraint}`, and treats a `{"ok": false}` verdict as triggered. Step `Parameters`: `declarationNames`, optional `guardrailServer`, optional `aiValidatorServer` (default `"ai-powered-tools"`), optional `maxInputBytes` (default 64 KiB): the request/result, as JSON, larger than that is never sent to the LLM and is "could not be checked". The worked examples are `go-gardening-demo/gardening-demo.cfg`'s `service-call-guardrails` (request) and `customer-details-no-audit` (result); `constraints_validation_test.go`'s `TestAIConstraintsValidation_FailsClosed` covers the verdict and every failure case against an in-process validator stand-in. Like `_filter_tool`, `ai_result_validator` is deliberately ungranted in every `accessRules` entry — reachable only via these steps' direct session call, never by an ordinary client.
- **AI constraints can be steered by the data they judge.** `Runtime.ValidateResult` keeps the data apart from the instructions — the task and constraint in the system message, the data in the user message inside a delimiter with a random per-call suffix the instructions point to — and accepts only an exact `{"answer": "ok"}`/`{"answer": "violation"}`. That makes injected text much less effective, not impossible: for a `block` rule that matters, pair the AI constraint with a deterministic one (a JSON-Schema constraint or a business validation tool) rather than relying on it alone.
- **Adding a declaration and the orchestration step that uses it**: always update `declarativeGuardrails` *first*. `_admin.update_declarative_guardrails` only returns once the `declarative-guardrail` server reports the new version via its `get_config_version` tool (see "Confirming a backend loaded an update" in `configsync.md`), typically a minute or two in k8s; an orchestration step that names a declaration the server hasn't loaded fails closed (`evaluate_declarations`: "unknown declaration").

## Business logic validation

Declarative constraint validation (above) is generic: `constraintsValidation`/`aiConstraintsValidation` judge a *target JSON value* (the request or result, whole) against a *rule* expressed either as a JSON-Schema fragment or free-form text, and that rule is all either mechanism ever knows about the call. Some checks can't be expressed that way at all — "does this purchase's *actual computed total*, after applying whichever deal discount the caller is eligible for, exceed a limit" requires re-running `purchase_products`' own pricing logic, which only `garden-online-store` has the code and private state (`store.productSupply`/`store.stock`) to do. **Business logic validation** is the third native-triggered-tool category for exactly this: hand-written Go, specific to one target tool's own semantics, hosted on that target tool's *own* server — not go-proxy, and not a generic schema/AI judge.

- **A business validation tool is an ordinary triggered tool with the ordinary call-authorization contract** (`CallAuthorizationInput` → `AuthorizationOutput`, see "Triggered tools / orchestration" (`orchestration.md`)) — nothing new about its wire shape. It can be wired directly as a `callAuthorization` step, the same as any other triggered tool, but that's not the typical way to use one (see the next bullet). `go-gardening-demo/servers/garden-online-store/main.go`'s `validate_store_requests` is the worked example: it decodes `CallRequest`'s `arguments` into `PurchaseProductsArgs`, then calls `fetchActiveDeals`/`fetchCustomerType` — the *exact same functions* `purchaseProducts` itself calls, unchanged — to get real deal-eligible pricing data, since a discovered triggered tool relays back through the proxy exactly like an ordinary backend call (see "Triggered tools / orchestration" (`orchestration.md`)). It computes a side-effect-free dry-run total via `computePurchaseTotal`, which shares `applyPurchase`'s own `purchaseFeasible`/`priceItem` helpers so the dry-run and the real purchase can never compute different numbers for the same input. Per its own spec: a purchase that would fail for an unrelated reason (unknown product, insufficient inventory) prices at **0**, not an error — `purchaseFeasible` decides feasibility first, and `computePurchaseTotal` returns `0` immediately if it fails, so a failing purchase can never be blocked on cost grounds.
- **`TargetServer` still matters even with relay capability** — relay lets `validate_store_requests` reach *other* backends (`garden-business-ops`, `garden-customer-admin`), but `proxy_utility.business_logic_constraints_validation` (the next bullet) itself runs *natively*, inside go-proxy's own process, and needs to know *which* server hosts the business validation tool a declaration names before it can dial it at all — that's what `CallAuthorizationInput.TargetServer` is for (see its own bullet below). `Runtime.SessionFor`, by contrast, lets a **native** step reach a sibling backend directly (e.g. `request_constraints_validation` calling `declarative-guardrail`) — a different mechanism for a different caller (native vs. discovered), not a superset/subset of the relay capability above.
- **Fail closed, per declaration.** Every check above ends each declaration in one of three ways: not triggered, triggered because it was violated, or triggered because it **could not be checked** (`triggeredDeclaration.uncheckedReason`: an invalid constraint, an unreachable validator or target server, a validator error — transport, `IsError`, an LLM error or timeout, an unparseable answer — or, for the AI steps, data larger than `maxInputBytes`). A triggered declaration's own actions decide what happens either way: `block` refuses the call, `alert` publishes an alert and lets it through, `log` logs. The alert's reason says "declaration X could not be checked: …" rather than "violates constraint", and a blocked call names it "X (could not be checked)". Only a failure that leaves no per-declaration actions to apply — `evaluate_declarations` itself unreachable or failing — is a step error, which fails the call (see `orchestration.md`). Tests: `constraints_validation_test.go`'s `TestConstraintsValidation_PartialFailureTolerance`, `TestAIConstraintsValidation_FailsClosed`, `TestBusinessLogicConstraintsValidation_FailsClosed`, `TestDispatchConstraintActions_UncheckedFollowsActions`.
- **`proxy_utility.business_logic_constraints_validation`** is the "typical way" to use a business validation tool — a fourth native call-authorization triggered tool alongside `request_constraints_validation` (registered in `doRunOn` the same way). It shares `constraintsValidationParameters`/`decodeConstraintsValidationParameters` and `evaluateDeclarations` with the JSON-Schema path (same `declarationNames`/optional `guardrailServer` `Parameters` shape), but interprets each returned `ActionResult.Constraint` differently: instead of a JSON-Schema fragment, it's a small JSON object naming **which** business validation tool to delegate to and an opaque parameters object meaningful only to it — `{"validationTool": "validate_store_requests", "parameters": {"maxTotalCost": 1000}}` (`businessValidationConstraint`, `constraints_validation.go`). For each declaration that decodes, `callBusinessValidationTool` dials `in.TargetServer` (see the next bullet) and invokes the named tool with a **synthetic `CallAuthorizationInput`** built from the original call's `User`/`Roles`/`TargetServer`/`TargetTool`/`CallRequest`/`ToolCallID`, but with `Parameters` replaced by the declaration's own opaque object (re-stringified) — the business validation tool can't tell whether it was invoked this way or wired directly as a `callAuthorization` step; both look identical on the wire. A declaration whose `Constraint` doesn't decode, a target server that can't be reached, or a business validation tool *call* that fails (network error, tool error, bad output) makes that declaration "could not be checked" — triggered, see "Fail closed, per declaration" below. The rest — `dispatchConstraintActions`/`publishConstraintAlert`, `tool-call-blocked`/`tool-call-alert` events — is reused unchanged from the JSON-Schema path. `go-gardening-demo/gardening-demo.cfg`'s `store-purchase-guardrails` orchestration and its `declarativeGuardrails`' `store-purchase-cost-limit` declaration are the real worked example; `proxyserver/testdata/orchestration_test.cfg`'s `business-constraint-guardrails`/`budget-limit` (guarding the in-process `orchestration-demo.budget_tool` + its own `validate_budget_tool` business-validation-tool stand-in, `platform_servers_test.go`) is the hermetic Go-test equivalent (Scenarios 11-12 in `TestPlatformServersOrchestration`) — `proxyserver/testdata/orchestration_test.cfg` carries an `internalAuth`/`selfUrl` section specifically so this scenario can exercise a real relay: `validate_budget_tool` itself relays a call back through the proxy to `orchestration-demo.say_hello` and requires it to succeed, so Scenario 12 (amount under the limit) only passes if that relay genuinely worked end to end, not just that headers were present.
- **`CallAuthorizationInput` carries `TargetServer`/`TargetTool`** (`contract.go`) specifically so `business_logic_constraints_validation` knows which server to dial without re-parsing `CallRequest`'s raw JSON `"name"` field — `Guard` (`orchestrate.go`) splits `reqParams.Name` (the namespaced tool name being guarded, e.g. `garden-online-store.purchase_products`) via a local `splitNamespacedToolName` (a copy of `dynamic_proxy`'s own unexported `removeFirstComponent` — this package already imports `dynamic_proxy` for `ReservedServerName`/`UtilityServerName`, but can't call an unexported function from it) once per `Guard` call, and passes both halves to every `callAuthorization` step for that call via `invokeCallAuthorization`. `ResultAuthorizationInput` deliberately doesn't carry them — nothing in this design needs them there.
- **A real gotcha this surfaced**: `in.CallRequest`'s concrete Go type depends on *how* a call-authorization tool was invoked. A **native** step (`request_constraints_validation`, `business_logic_constraints_validation` itself) receives it directly as the `json.RawMessage` `Guard` built — no wire round-trip, so a `callRequest.(json.RawMessage)` type assertion (`constraints_validation.go`'s `callRequestToolName`) works. A **discovered** tool — including a business validation tool invoked either directly as a `callAuthorization` step or relayed through `business_logic_constraints_validation` — receives it after a genuine MCP `tools/call` round-trip, where `encoding/json` decodes a JSON object into the untyped `CallRequest any` field as `map[string]any`, never `json.RawMessage`. A type assertion there fails closed on every real invocation — and `garden-online-store`'s own unit tests won't catch it, since they call the handler in-process; only `TestPlatformServersOrchestration` Scenarios 11/12 exercise the wire path. The pattern any business validation tool should follow is `json.Marshal(in.CallRequest)` then `json.Unmarshal` into the target struct, which handles both concrete types uniformly rather than assuming one.
- **Config/CLI wiring**: `go-gardening-demo/initial-data/declarative_guardrails.json` (an array of new `guardrailcfg.RawDeclaration`s) and `orchestration.json` (a `triggered_tools_runtime.OrchestrationConfig` fragment — new/updated `orchestrations` plus `toolMappings` to prepend) are seeded by `cli init` (`go-gardening-demo/cli/init.go`'s `runInit`, after `update_access_rules`) via two new admin commands, `admin update_declarative_guardrails`/`admin update_orchestration` (`go-gardening-demo/cli/admin.go`), which follow `runUpdateAccessRules`'s own export-merge-update shape against `_admin.export_declarative_guardrails`/`update_declarative_guardrails` and `_admin.export_orchestration`/`update_orchestration`: `configmerge.MergeDeclarativeGuardrails` replaces a same-named declaration and unions the actions catalog (so a repeat run converges rather than duplicating or failing on an unknown action name); `configmerge.MergeOrchestration` upserts orchestrations by name and rebuilds `toolMappings` as the new file's own mappings (deduped by pattern) followed by whatever wasn't superseded — new mappings first, so a specific pattern like `garden-online-store.purchase_products` reliably precedes a pre-existing catch-all `"*"`, matching `toolMappings`' first-match-wins evaluation. `gardening-demo.cfg` itself also carries the same final `declarativeGuardrails`/`governanceOrchestration` content directly, so a fresh deploy (which seeds ConfigMaps only when they don't already exist — see "Configuration sync (configsync)" (`configsync.md`)) picks it up without needing `cli init` to run first.
- **`go-gardening-demo/configmerge`/`go-gardening-demo/patchcfg` keep a committed cfg's baked-in copy from drifting out of sync with `initial-data`**: the three sections above (`client_access_rules.json`/`declarative_guardrails.json`/`orchestration.json`) and a committed `*.cfg`'s own `accessRules`/`declarativeGuardrails`/`governanceOrchestration` sections are, at any given moment, two independent copies of overlapping content — the cfg needs its own complete copy because go-proxy's self-seeding (`configsync.Writer.EnsureSeeded`, "Configuration sync (configsync)" (`configsync.md`)) makes the cfg authoritative the *moment go-proxy starts*, before `cli init` (or anyone) has run against a live cluster. `go-gardening-demo/cli/admin.go`'s merge algorithms (`MergeAccessRules`/`MergeDeclarativeGuardrails`/`MergeOrchestration`) are extracted into the importable `go-gardening-demo/configmerge` package specifically so a *second* package-main binary, `go-gardening-demo/patchcfg`, can reuse the exact same logic **offline** — no live proxy involved at all — to patch a committed cfg's baked-in section directly from the `initial-data` files (`patchcfg [-data-dir DIR] <cfg-file> [<cfg-file> ...]`). It only ever patches a section the target cfg already has (never adds one a cfg deliberately omits — e.g. `gardening_demo_test.cfg` has no `governanceOrchestration` section and stays that way), and preserves every other top-level key and the document's own top-level key order untouched (`orderedDocument`/`writeOrderedDocument`) — only the patched sections' own content changes. Run it after regenerating `client_access_rules.json` (via `gendata`) or hand-editing `orchestration.json`/`declarative_guardrails.json` (gendata doesn't generate either of those two at all) to keep every committed cfg's baked-in copy in sync, the same way `cli init` keeps a *live cluster* in sync.
