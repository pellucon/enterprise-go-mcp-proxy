# NATS event system

> Cross-references to sections elsewhere name their file; see `README.md` for the index.

## NATS event system

Go package `events` at `events/` (import path `github.com/pellucon/enterprise-go-mcp-proxy/events`) is a small NATS-based publish/subscribe layer, independent of `triggered_tools_runtime` (no shared code — the two happen to be used together in the platform-mcp-servers/go-proxy itself below, but `events` doesn't know about triggered tools or orchestration at all). Events are published when interesting things happen (a rejected call, a completed or failed call); dedicated MCP servers subscribe and either log or expose tools to inspect them.

- **`events.Event`** (`events/event.go`): `Type`, `Time`, `Title`, `Text` mandatory; `Subtype`/`Metadata` optional. `Subject()` derives the NATS subject as `events.<type>.<subtype-or-"_">` — the `"_"` placeholder when `Subtype` is empty keeps every subject the same token-count, so both `events.>` and `events.<type>.>` wildcard subscriptions match uniformly regardless of whether a given event has a subtype.
- **`events.Dictionary`** (`events/dictionary.go`): a JSON-authored description of every event type a `Client` may publish. The real source of truth is `proxy-server.cfg`'s `eventDictionary` section (see "Configuration sync (configsync)" (`configsync.md`)); `proxyserver/testdata/event_dictionary_test.json` (repo root, committed — not sensitive, it's data rather than key material so there's no reason to generate it fresh per run) is only the local-dev/test default for the `-events-dictionary` flag. For each event type, its closed set of allowed `subtypes` (if it uses subtypes at all — empty means the type doesn't use subtypes, and an event of that type must then have an empty `Subtype`), and which metadata keys are required/optional, their value type (`string`/`number`/`date`/`boolean`/`json` — there is no array type, so a list value like a caller's roles uses `"json"`), and (for `string` fields) an optional closed `allowedValues` set. `Dictionary.Validate` fails closed: an unknown event type, an undeclared subtype, a missing required key, a wrong-typed value, or a `string` value outside `allowedValues` are all errors. Simpler than `triggered-tools-runtime/validate.go`'s `jsonschema.For[T]` approach since this dictionary is hand-authored JSON, not derived from a Go struct.
- **`events.Client`** (`events/client.go`) wraps a `*nats.Conn` (`github.com/nats-io/nats.go`) plus a swappable `*Dictionary`. `NewClient(natsURL string)` returns `(nil, nil)` for an empty `natsURL` (mirroring `configsync.Connect`'s convention) — a generic package-level behavior other callers of this package may still rely on, but `event-aggregator` and go-proxy itself always pass a non-empty `-nats-url`/`natsUrl` (see below), so their own `eventsClient` is never nil. `Publish` fails closed if the event fails `Dictionary.Validate` (or no dictionary has ever been set — see `SetDictionary` below), and `Subscribe` applies the same check to every received event — plus that it arrived on its own subject (`Event.Subject()`) — dropping anything else, so a message that didn't come from a validating `Publish` is never handed on. What a client may publish or subscribe to is enforced by NATS itself (see "NATS authentication and TLS" below). `NewClient`'s `nats.Connect` call sets `nats.RetryOnFailedConnect(true)` (plus `DisconnectErrHandler`/`ReconnectHandler` log lines) deliberately: in k8s, a backend's own pod can easily start before NATS has finished rolling out — without this option `nats.Connect` fails outright on the very first dial attempt, with no retry, indistinguishable from a real permanent outage. With it, `NewClient` succeeds immediately and the connection retries in the background for about 2 minutes (`nats.DefaultMaxReconnect`×`nats.DefaultReconnectWait`) before giving up — comfortably covering a normal startup race without requiring deploy-order sequencing to be exact. A genuinely unreachable NATS still surfaces, just later (via a failing `Publish`/`Subscribe` call, the reconnect log lines, or `/healthz` below) rather than as a startup crash — this is deliberate: blocking `main()` on a synchronous NATS dial would reintroduce exactly the startup-race problem `RetryOnFailedConnect(true)` exists to avoid.
- **NATS is a hard dependency for go-proxy itself and `event-aggregator`** — each fails startup outright on a missing/unreachable-at-parse-time `natsUrl`/`-nats-url` (go-proxy's `doRunOn` checks `proxyCfg.NatsURL == ""` explicitly before `configsync.Connect`; event-aggregator has no `-events-publish`/`-events-subscribe` opt-out flag, it always builds `events.NewClient` and a `configsync.Watcher[Dictionary]` unconditionally). `declarative-guardrail` is the deliberate exception: its own `-nats-url` flag is still optional, since it only uses NATS for config hot-reload, never events (see "Configuration sync (configsync)" (`configsync.md`)) — it is not part of this requirement and has no `/healthz`. Because `RetryOnFailedConnect(true)` means a *reachable-but-not-yet-connected* NATS never fails the initial dial, readiness (not liveness) is what actually gates traffic: both go-proxy and event-aggregator expose a `GET /healthz` (`events.Client.IsConnected()`, wrapping `nats.Conn.IsConnected()` — go-proxy additionally checks its own separate `natsConn`, see "Configuration sync (configsync)" (`configsync.md`)) returning 200 when connected, 503 otherwise. Each server mounts it as a sibling `http.ServeMux` route alongside the existing MCP handler at `"/"` — for go-proxy specifically, `/healthz` sits outside `protectedHandler`/`createMiddleware` entirely, since a k8s probe carries no JWT and shouldn't need one. `k8s/go-proxy-deployment.yaml` and `platform-mcp-servers/event-aggregator/k8s/deployment.yaml` point `readinessProbe` at `httpGet: {path: /healthz, ...}`; `livenessProbe` stays `tcpSocket` — a NATS blip should take a pod out of Service rotation, not get it killed and restarted.
- **Demo event types** (`proxyserver/testdata/event_dictionary_test.json`; `event-aggregator`'s CWD-relative `-events-dictionary` default `./event_dictionary_test.json` doesn't find it from the repo root — k8s always passes the flag explicitly, and a manual local run should pass `-events-dictionary proxyserver/testdata/event_dictionary_test.json`): `alert` (subtypes `tool-call-blocked`/`result-blocked`/`tool-call-alert`/`result-alert`; metadata `user`/`roles`/`tool`/`reason` all required — `roles` is `"json"`-typed, carrying the caller's actual `[]string`, not a delimited string); `tool-request` (subtypes `request-blocked`/`request-ok`; metadata `user`/`roles`/`tool`/`request` required, `reason` optional — absent on `request-ok`; no `result` key at all, since this event always fires before any call is attempted — see `Runtime.Guard` above); and `tool-request-result` (subtypes `result-blocked`/`call-failed`/`call-succeeded`, which alone encode the outcome — there's no separate authorized bool; metadata `user`/`roles`/`tool`/`request` required, `result` optional — absent when no backend call was made or the call itself failed — and `reason` optional — absent only on `call-succeeded`). Recall `Validate` only checks a required key is *present*, not non-empty — this matters because `triggered_tools_runtime.ResultAuthorizationInput` (unlike `CallAuthorizationInput`) carries no `CallRequest`/tool name, so the `authorization-mcp-server` stand-in's `publishAlert` always sets all four `alert` metadata keys unconditionally (never omitting one), and a `result-blocked` alert's `tool` is genuinely just an empty string, not a real tool name — only `tool-call-blocked` alerts (from the call-authorization phase) can supply a real one. `tool-call-alert`/`result-alert` are reserved for `proxy_utility.request_constraints_validation`/`result_constraints_validation`'s `"alert"` action (see "Declarative constraint validation" (`guardrails.md`)) — that stand-in never publishes them.
- **Producers**: `platform_servers_test.go`'s in-process `authorization-mcp-server` stand-in publishes an `alert` from all four of its rejection paths (`call-authorization`, `call-authorization-role-check`, `result-authorization`, `result-authorization-length-check`), fire-and-forget, a publish error is logged, never surfaces to the tool's own authorization return value. (In a real deployment only go-proxy may publish events; the stand-in runs against an unauthenticated embedded NATS server.) `proxy_utility.request_constraints_validation`/`result_constraints_validation` are the other `alert` producer (see "Declarative constraint validation" (`guardrails.md`)). go-proxy's own orchestration engine (`triggered_tools_runtime.Runtime.Guard`) is the sole producer of both `tool-request` (via the `RequestEventPublisher` seam `main.go` installs as `publishToolRequest`) and `tool-request-result` (via the `EventPublisher` seam installed as `publishToolRequestResult` — see "Triggered tools / orchestration" (`orchestration.md`)), publishing directly with no tool invocation in between.
- **Consumers**: `platform-mcp-servers/event-aggregator` is an ordinary (non-triggered — no `_meta` annotation) MCP server and the sole consumer of every event published on `events.>`. At startup it subscribes to `events.>`; each delivered event is first checked against a live, admin-updatable **ingestion filter** (`events.Filter`, same field shape/semantics as `list_events`' own query filter below — an empty filter matches everything) and dropped before it ever reaches any tier if it doesn't match. A matching event feeds a **tiered store**: a fixed-capacity, mutex-guarded, in-memory ring buffer (`ringBuffer` in its `main.go`, the "hot" tier); once full, the oldest event is evicted and spilled to a local append-only JSONL segment log (package `eventlog`, the "cold" tier) instead of being dropped, unless `-event-log-dir` is unset, in which case there's no disk tier and eviction drops the event (this server's original v1 behavior). A background `eventlog.Archiver` periodically ships (or, by default, discards — see `eventlog.DiscardArchiverTransport`) rolled log segments once they cross a configured age or total-size threshold, keeping local disk usage bounded even with no real external archive destination configured. Which implementation ships a segment (and its own properties) is selected by the `eventAggregation` config's `archiverTransport` field, resolved at runtime against a package-level registry (`eventlog.RegisterArchiverTransport`/`eventlog.NewArchiverTransport`) that every `ArchiverTransport` implementation populates from its own `init()` — adding a new one (e.g. an S3 uploader) is "drop a new file in `eventlog/`", no other file needs editing. The ring buffer's capacity, the ingestion filter, and the log's age/size thresholds are all part of the live-updatable `eventAggregation` config section (see below). It exposes `list_events` (most-recent-first, every filter field optional and AND'd together: exact `type`/`subtype`/`user`/`toolCallId`, `roles` — matches if the event has at least one of the given roles — and wildcard `tool`/`reason` via the same `access_control.GlobMatch` `*`-crosses-everything semantics `triggered_tools_runtime`'s `toolMappings` already uses; optional `since`/`cursor` bound and paginate a query across both tiers via a tier-handoff — memory is drained first, then disk, since eviction keeps the two tiers contiguous and non-overlapping in arrival order — returning an opaque `nextCursor` for the next page, with a clear error if a cursor's segment has since been archived away, and `eventlog.ErrInvalidCursor` for an offset past the end of its segment: the cursor is client-supplied, and reading backward from past EOF would grow the read buffer until memory ran out), `get_event_stats` (cumulative counts of every event this process has ever been given since its own last restart, via a dedicated `eventStats` counter, one count per event under its most specific key — `"type.subtype"` if the event has a subtype, else just `"type"`, never both, so e.g. `"tool-request-result.call-succeeded"` alone, not also a redundant `"tool-request-result"` carrying the same total — independent of the ring buffer's capacity/eviction and the disk tier entirely, so it stays O(1) regardless of how much history exists on disk, unlike a `list_events`-style tier-handoff walk would be; both real NATS ingestion (gated by the ingestion filter) and `load_events`' bulk loads call `record` — a caller seeding canned demo data (e.g. go-gardening-demo's own `sample-events.json`, see below) expects the stats to reflect it exactly as if it had arrived for real, not stay empty until real traffic shows up; `reset_events` is the one exception, since it only clears the buffer's displayable contents, never these counts), and `load_events` (replaces the buffer's entire contents with a client-supplied events array — bypasses NATS/the event dictionary/ingestion filter entirely, purely for seeding realistic-but-canned data to test `list_events`'s filters against (its counts toward `get_event_stats` are real, per that bullet's own note, even though the events themselves are canned); `cli`'s `load-events -file <path>` command reads a local events JSON file client-side and sends it as the tool's `events` argument — the server itself never reads a file for this. `go-gardening-demo/initial-data/sample-events.json`, generated by `go-gardening-demo/gendata`'s `buildSampleEvents`, is the canonical such dataset: it reverse-engineers the plausible `garden-online-store.purchase_products`/`purchase_fulfilled`/`add_supply_order`/`mark_supply_order_fulfilled` calls that would have produced `online_customer_orders.json`/`supply_orders.json` — one `tool-request-result`/`call-succeeded` event per real order/supply-order record — then sprinkles in a `tool-request`/`request-ok` for a random subset of those calls, a `tool-call-alert`/`result-alert` for a random subset of unusually high-value ones, and a small fixed set of made-up alerts for attempts that never happened at all — a `tool-call-blocked` alert paired with a `tool-request`/`request-blocked` event (a call-authorization-style rejection, decided before the real call would ever run), or a `result-blocked` alert paired with a `tool-request-result`/`result-blocked` event (a result-authorization-style rejection, after the call would have run) — both of a pair sharing the same `toolCallId`, matching the real two-phase orchestration model (see "Triggered tools / orchestration" (`orchestration.md`)). `go-gardening-demo/cli`'s own `init` command — see its `init.go`'s `runLoadSampleEvents` — loads it as one of its last two steps by calling `event-aggregator.load_events` directly (event-aggregator isn't one of `go-gardening-demo/servers/*` at all, so unlike every other `initial-data/*.json` file this one has no entry in `tools.go`'s `sections` table to go through); it can also be loaded standalone via the other CLI's own `cli load-events -file <path>` (`cli/`, not `go-gardening-demo/cli`). Core-NATS-only, no JetStream — fire-and-forget pub/sub, no persistent stream on the NATS side, so a NATS restart doesn't replay history; this was a deliberate v1 scope decision, not an oversight (event-aggregator's own on-disk tier is a separate, independent durability mechanism, not JetStream-backed persistence). "platform" (as in `platform-mcp-servers/`) names the broader server-grouping convention, unrelated to the narrower "triggered tool" `_meta` mechanism.
- **Tiered storage assumption**: the whole design above (in-process ring buffer + disk writer + archiver, no cross-process coordination) assumes `event-aggregator` runs as a single pod (`replicas: 1`, per its own `k8s/deployment.yaml`) — if that ever changes, this per-process design needs rethinking. The on-disk tier is backed by a PVC (`platform-mcp-servers/event-aggregator/k8s/pvc.yaml`), not `emptyDir`: `emptyDir` survives container restarts but not pod rescheduling/deletion, which would silently lose the whole disk tier. `ReadWriteOnce` access is sufficient given the single-pod assumption.
- **NATS authentication and TLS.** NATS refuses anonymous and plain-text connections. `k8s/nats/nats.conf.tmpl` gives each component that connects its own user, allowed exactly the subjects it needs: go-proxy publishes `events.>` and `_system.config.>` and subscribes to `_system.config.>`; event-aggregator subscribes to `events.>` and its own sections' config pings and publishes nothing; declarative-guardrail, rate-limiter and ai-powered-tools only subscribe to their own sections' pings. So only go-proxy can publish events, only event-aggregator can read them, and no component can send another's config pings. `scripts/deploy.sh`'s `ensure_nats_secrets` creates, once each, a private CA and NATS's server certificate (`nats-tls`; the CA key is discarded after signing), a random password per component (`nats-client-<component>`, also holding `user` and `ca.crt`), and renders `nats-server-config` from the template; a hash of the rendered config, as a pod annotation, restarts NATS exactly when it changes. Each component's Deployment mounts its own Secret at `/etc/nats-client` and sets `NATS_CREDENTIALS_DIR`; `natsclient.Options` (used by both `events.NewClient` and `configsync.Connect`) turns that into `nats.UserInfo` plus `nats.RootCAs`. No credentials mounted means an anonymous connection, which the server refuses. Adding a NATS client means a user in the template, an entry in `deploy-proxy.sh`'s `NATS_COMPONENTS`, a Secret mount, and its `app` label in `k8s/networkpolicy-allow-backends-to-nats.yaml`. Tests: `natsclient/natsclient_test.go` loads the real template into an embedded NATS server with TLS and checks every user's permissions and that anonymous, wrong-password and plain-text clients are refused.
- **What audit events carry.** `tool-request` and `tool-request-result` carry the call's `request`, and `tool-request-result` its `result`, each through `main.go`'s `auditPayload`: anything over `maxAuditPayloadBytes` (16 KiB) as JSON is replaced by `{"truncated": true, "bytes": N, "sha256": "..."}`, which keeps every event well under NATS's 1 MB message limit (an event over it isn't delivered at all) and bulk data out of the audit trail. A `result-blocked` event carries no `result`: a result a guardrail kept from the client mustn't reach the audit trail instead. Tests: `audit_payload_test.go`.
- **Limits every published event gets** (`events.Client.Publish`): its title, text and top-level string metadata values are cut to 4 KiB (`capText`, at a UTF-8 boundary, marked as truncated) - some carry text a backend controls, such as a failed call's error, and an event over NATS's 1 MB limit would vanish along with its audit record. Event type and subtype names may only use letters, digits, `-` and `_` (`validateShape`): they're tokens of the event's NATS subject, so `.`, `*`, `>` or whitespace would change which subject it is. Tests: `events/limits_test.go`.
- **Loaded events are marked.** Every event `event-aggregator`'s `load_events` adds (demo data, the stress test) gets `metadata.imported = true`, overwriting any value given, so a loaded event can't pass as a real audit record from go-proxy. Test: `main_test.go`'s `TestLoadEventsMarksImported`. `load_events`/`reset_events` stay available to the administrator role only, as the demo seed and the stress test use them.
- **Archiving is bounded**: each HTTP archiver upload has a 10-minute deadline (`uploadTimeout`), so an endpoint that never answers fails the upload (retried next sweep) instead of stalling archiving while the local log grows.
- **k8s**: `k8s/nats-deployment.yaml`/`k8s/nats-service.yaml` — an unmodified official `nats:2.10-alpine` image (not built from this repo's `Dockerfile`) run with `-c /etc/nats-config/nats.conf`, `ClusterIP` Service on port `4222`, no JetStream flags, no PVC. `k8s/networkpolicy-allow-backends-to-nats.yaml` allows ingress to NATS only from the five components above, by their `app` label — the only pods besides go-proxy itself that reach something directly rather than being reached through the proxy. The event dictionary is seeded into the `event-dictionary-override` ConfigMap by `scripts/deploy.sh`'s `deploy_proxy` (from `proxy-server.cfg`'s own `eventDictionary` section — see "Configuration sync (configsync)" (`configsync.md`)), mounted at `/app-run` in every backend that publishes or subscribes (and, via a separate mount, `/etc/proxy-server/event-dictionary-override` for go-proxy itself — see `k8s/go-proxy-deployment.yaml`) and live-reloadable via `_admin.update_event_dictionary`. `deploy_proxy` also waits on the `nats` Deployment's own rollout (`kubectl rollout status deployment/nats --timeout=120s`) right after applying `k8s/`, before doing anything else — without this, `--deploy-platform-servers`/`--deploy-all` could start deploying event-publishing/subscribing backends before NATS was actually ready (which is why `--deploy-platform-servers` also does its own such wait independently of whether `--deploy-proxy` ran in the same invocation), and (combined with `events.Client.NewClient`'s own retry-on-connect tolerance above) this is belt-and-suspenders: the wait avoids the race in the common case, the client-side retry tolerates it if the wait isn't enough or a backend is deployed standalone via `deploy.sh --deploy-server <path>` without the category wait.
- **Which components hold a `Watcher[Dictionary]`**: `event-aggregator` wires one (`onChange = eventsClient.SetDictionary`, see "Configuration sync (configsync)" (`configsync.md`)) — and so does go-proxy itself, in `main.go`'s `doRunOn`, built alongside its own `eventsClient` so `triggeredRuntime`'s `EventPublisher` can actually call `Publish`.
- **Test**: `events/client_test.go` is a hermetic unit-test layer for the package alone — an embedded, in-process `github.com/nats-io/nats-server/v2/server` instance on a random port (no real NATS binary or k8s needed), covering the publish/subscribe round-trip, the empty-`natsURL` no-op case, and all dictionary-validation failure modes. `event_system_test.go` (root package) is the end-to-end demo test proving the real integration: in-process stand-ins for the authorization/aggregator servers (duplicated logic, same "package main can't cross-import another package main" constraint as `platform_servers_test.go`'s stand-ins) plus an embedded NATS server, wired into a real orchestration via `startTestBackend`/`startTestProxy` with `natsUrl` pointed at that embedded server, proving a rejected call produces both an `alert` event (from the authorization stand-in) and a `tool-request-result`/`result-blocked` event (from go-proxy's own orchestration engine), and a successful call produces a `tool-request-result`/`call-succeeded` event — all independently observable by a subscriber and via the aggregator's own `list_events` tool called through the proxy. One non-obvious thing this test caught: the tool name a triggered tool (or go-proxy's own published event) sees is the *namespaced* name (e.g. `event-demo.bad_tool`), not the bare tool name — the namespace is only stripped later, when `dynamic_proxy.Gateway.registerTool`'s handler actually dispatches to the backend session.
