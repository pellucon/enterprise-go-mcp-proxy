# Auth, internal identity assertions, and tool-call IDs

> Cross-references to sections elsewhere name their file; see `README.md` for the index.

## Auth and access control

- `auth/auth_service.go`: `auth.Verifier` (built once at proxy startup via `auth.NewVerifier`) parses/verifies RS256 JWT bearer tokens — signature, algorithm (`WithValidMethods`), required expiry (`WithExpirationRequired`), and, if configured, `iss`/`aud`. Its `Config` (JSON-tagged: `publicKeyPath`/`jwksUrl`/`issuer`/`audience`/`resourceUrl`/`roleClaim`) selects the key source: a static PEM public key (`PublicKeyPath`, the default) or a JWKS endpoint (`JWKSURL`, which takes precedence when set) — the JWKS path uses `github.com/MicahParks/keyfunc/v3` to fetch/refresh keys in the background and select by the token's `kid`, so keys can rotate without restarting the proxy. `config.go`'s `loadProxyConfig` parses the combined config file's `auth` section directly into an `auth.Config`; `doRun` assigns it to the package-level `authConfig` var (only if that section was present — see `ProxyConfig.Auth`'s pointer-nil convention), which `runProxyServer` passes to `auth.NewVerifier` — a bad/unreachable JWKS URL fails fast there at startup rather than on the first request.
- `authenticateRequest` (`middleware.go`) is the shared two-path auth check both `createMiddleware` and `main.go`'s `HTTPMiddleware` call: an ordinary client's `Authorization` header, or a backend's relayed identity assertion (see "Internal identity assertions") when that header is absent. On the client path, if `authConfig.RoleClaim` names a claim other than `"role"`, its value is copied into `claims["role"]` so every downstream consumer of `access_control.RolesFromClaims` keeps reading one normalized key regardless of what a real IdP (Auth0/Okta/Azure AD/etc.) actually calls its roles/groups claim — most don't emit a claim literally named `"role"`, which is `demo-authorization-server`'s own convention, not a standard. The relay path never needs this: internal assertions are always minted by this proxy's own `auth.Signer` with a literal `"role"` claim (`auth/signer.go`'s `Sign`).
- `demo-authorization-server` stands in for that real IdP, so it also supports minting tokens under a configurable role claim, via its own `-role-claim` flag (`demo-authorization-server/main.go`, threaded through `newState`/`tokenSigner.mintAccessToken` in `server.go`/`keys.go`) — empty (default) keeps minting under `"role"`, matching every existing test's assumption. `proxy-server.cfg`'s `auth.roleClaim` is set to `"app_roles"`, and `scripts/deploy.sh`'s `start_demo_auth_server` passes the matching `-role-claim app_roles`, specifically so the local demo exercises this remapping against a real minted token end to end, not just `resource_metadata_test.go`'s synthetic one. `proxyserver/testdata/integration_test.cfg`/`orchestration_test.cfg` deliberately don't set `roleClaim`: those configs are only ever exercised by in-process Go tests that mint tokens directly (`mcp_client_test.go`'s `GenerateTestTokenForRole` and friends, hardcoded to the `"role"` claim, shared by many unrelated tests) rather than by `demo-authorization-server`, so there'd be nothing real to gain and a lot of unrelated tests to update.
- `createMiddleware(verifier)` in `middleware.go` wraps every MCP method call (`AddReceivingMiddleware`): it calls `authenticateRequest` and returns an error immediately if that fails (missing header, bad signature, expired, etc.) rather than proceeding with a nil/partial token, then enforces access before delegating.
- `HTTPMiddleware` (`main.go`) is a separate, earlier gate wrapping the whole MCP handler at the raw HTTP layer (`protectedHandler := HTTPMiddleware(verifier, mcpHandler)`), not just per-MCP-method like `createMiddleware`. It exists for a generic MCP client (one that doesn't already know which authorization server to use out-of-band, unlike this repo's own `cli`/`oauthclient`): without it, an unauthenticated request would reach all the way into JSON-RPC dispatch and fail there as a JSON-RPC error inside an HTTP `200` — invisible to a client that isn't already expecting to need to log in. `HTTPMiddleware` reuses the same `authenticateRequest` two-path check `createMiddleware` uses (so the relay path — a backend calling back into the proxy with no `Authorization` header — passes this gate for free, no separate carve-out needed) and, on failure, returns a real HTTP `401` with `WWW-Authenticate: Bearer` (plus a `resource_metadata="<.../.well-known/oauth-protected-resource URL>"` param, only when `authConfig.ResourceURL` is configured) — the signal the MCP Authorization spec, and the go-sdk's own client-side `auth.AuthorizationCodeHandler`, rely on to start OAuth discovery at all. `createMiddleware` still re-validates independently afterward; this is an additional, earlier signal, not a replacement, and deliberately narrow in scope: role/access-rule rejections (wrong role for a tool) still surface as an in-band JSON-RPC error, not `401`/`403` — the caller already successfully authenticated in that case, so re-triggering the OAuth flow would be wrong.
- When `authConfig.ResourceURL` is set, `runProxyServerOn` also mounts `GET /.well-known/oauth-protected-resource` (RFC 9728 Protected Resource Metadata) — deliberately unauthenticated, like `/healthz`, since a generic client fetches this before it has any credential at all. Built via the go-sdk's own `auth.ProtectedResourceMetadataHandler`/`oauthex.ProtectedResourceMetadata` (`github.com/modelcontextprotocol/go-sdk/auth`, imported as `sdkauth` in `main.go` to avoid colliding with this repo's own `auth` package of the same name) rather than hand-rolled, since there's no existing implementation of this to preserve. It is mounted at the root path and, when `ResourceURL` has a path (e.g. `/mcp`), also at RFC 9728's path-inserted variant (`/.well-known/oauth-protected-resource/mcp`, `protectedResourceMetadataPaths`), which spec-compliant MCP clients try first. The 401 hint's URL (`protectedResourceMetadataURL`, built on `forwarded.BaseURL` in the `forwarded/` package) is derived from the request, but prefers `X-Forwarded-Proto`/`X-Forwarded-Host` when present, so behind a TLS-terminating L7 proxy (ingress-nginx) it advertises the public `https://` host; with no such headers (direct connection, or k3s's L4 klipper) it's the plain request-derived URL. It deliberately isn't derived from `ResourceURL`, which would point a standalone binary on `:8081` at port 80. Spoofed headers only change the hint in the spoofer's own 401. `authConfig.Issuer` doubles as the document's `authorization_servers` entry — for a real third-party IdP this is already its real, discoverable base URL by construction; for `demo-authorization-server` it must be pointed at a real fetchable URL via its own `-issuer` flag (`demo-authorization-server/main.go`) rather than the non-URL placeholder `proxy-server.cfg` uses today, for this to be meaningful — a config-only change, not a code change.
- `access_control/access_policy_engine.go` + the combined config file's `accessRules` section (`AccessConfig.ClientAccessRules`, JSON key `clientAccessRules` — named to read clearly as client-facing role rules, distinct from any future non-role-scoped fields on the same section): role → allowed-pattern rules (`allowed_tools`, `allowed_prompts`, `allowed_resources`, `allowed_resource_templates`) via the shared `AccessPolicyEngine` (`IsToolAuthorized`/`IsPromptAuthorized`/`IsResourceAuthorized`/`IsResourceTemplateAuthorized`, all built on the same `matchAny` primitive). `matchAny` matches the *role* pattern with `filepath.Match` (e.g. role `"development.*"` matches role `"development.manager"`) but matches the *name/pattern* side with the exported `GlobMatch`, not `filepath.Match` — `filepath.Match`'s `*` refuses to cross a `/`, which would silently break wildcard rules for anything containing a slash (virtually every resource URI, e.g. `file:///a.txt`); `GlobMatch` treats `*` as matching any characters, including `/`. (`GlobMatch`/`RolesFromClaims` are exported specifically so `triggered-tools-runtime` and `middleware.go`'s orchestration wiring can reuse the same wildcard/role-normalization semantics — see "Triggered tools / orchestration" (`orchestration.md`).) Applied both to block unauthorized `CallTool`/`GetPrompt`/`ReadResource` requests and to filter `ListTools`/`ListPrompts`/`ListResources`/`ListResourceTemplates` results (`filterTools`/`filterPrompts`/`filterResources`/`filterResourceTemplates`, all four built on the shared generic `filterList[T]` helper) so clients only see tools/prompts/resources/resource-templates their role can access. `IsResourceAuthorized`/`filterResources` and `IsResourceTemplateAuthorized`/`filterResourceTemplates` match against the *namespaced* URI/URITemplate (`<serverName>:<uri>`, see "Gateway / tool-prompt-resource-template registration" (`gateway.md`)), not the backend's original URI. Tool names prefixed `_admin.` (the reserved namespace for the proxy's own native admin tools, `dynamic_proxy.ReservedServerName`) are a special case, authorized solely by an exact check for the **administrator role** regardless of the configured rules. The administrator role's name comes from the cfg's top-level `roleMapping` section (`{"administrator": "<role>"}`, `access_control.RoleMapping`/`ParseRoleMapping`; required with no default: absent, `null`, or an empty/blank `administrator` all fail startup, so every deployment names its administrator role explicitly; every repo cfg and root-test fixture maps it to `"admin"`). It's passed to `NewAccessPolicyEngine` once in `doRunOn` and kept in an immutable field that `Update` never touches, and `roleMapping` is deliberately not a configsync section: the admin tools are what change every live section, so letting them (or an `accessRules` update) change who counts as an administrator would let one admin hand the gateway to an arbitrary role or lock every admin out. `_admin.export_full_config` round-trips it read-only (`roleMappingConfig`); there's no update tool. `hasAdministratorRole` is a literal comparison, never a glob, and an empty administrator role matches nothing. Tests: `access_control/role_mapping_test.go`, `config_test.go`'s `TestLoadProxyConfigRoleMapping`, `configmap_test.go`'s `TestAdministratorRoleMapping` — see `_admin.update_role_permissions`/`_admin.export_role_permissions`/`_admin.update_orchestration`/`_admin.export_orchestration` in `admin_tools.go`'s `registerAdminTools`.
- Trust boundary: once `isToolRoleAuthorized`/`isPromptRoleAuthorized`/`isResourceRoleAuthorized`/`isResourceTemplateRoleAuthorized` passes, the backend receives the call via the proxy's own client session with no per-user context — backends implicitly trust that they're only reachable through the proxy. That's enforced at the network level by NetworkPolicies: `k8s/networkpolicy-default-deny.yaml` + `k8s/networkpolicy-allow-proxy-to-backends.yaml` in `mcp-proxy`, and `go-gardening-demo/k8s/networkpolicy-default-deny.yaml` + `networkpolicy-allow-ingress-from-proxy.yaml` (cross-namespace, `namespaceSelector` AND `podSelector` on `app: go-proxy`) in `gardening-demo` — see "Namespace layout" (`discovery.md`). Enforcement depends on the cluster's CNI actually honoring NetworkPolicies (on one that doesn't, they're silently no-ops), and a backend in any other namespace gets no policy from this repo at all — e.g. `examples/discovery` ships its own. So isolation is still a deployment guarantee in the general case, not something the proxy itself can check.

- **go-proxy's own backend credentials (`backendauth/`)**: distinct from, and never a substitute for, the client's token. A backend that requires credentials gets a Secret in go-proxy's own namespace assigned to it by go-proxy's config — the discovery section's `k8sCredentials` map (`"<namespace>/<service>"` → Secret name, applied in `k8s_discovery.go`'s `buildServerMap`) or a static entry's `credentialsSecret` — carried as `ServerAttributes.CredentialsSecret`. The backend itself never chooses (see "Discovery trust rules" in `discovery.md`). `backendauth.Client(base, secretName)` wraps every backend client (the four `dynamic_proxy` pollers, `session_proxies.go`'s `createMCPSession`, `triggered-tools-runtime`'s `session`) and returns `base` unchanged when no secret is named. Secret data holds exactly one of `token` (Bearer), `header`+`value`, or `tokenUrl`+`clientId`+`clientSecret` (+`scopes`, `audience`) for the OAuth client-credentials grant (`golang.org/x/oauth2/clientcredentials`, token reused until near expiry). `Store` re-reads a Secret at most every minute (`Default`), keeps the existing credential — and its cached token — when the data is unchanged, keeps the last good one through a transient read error, and fails closed otherwise (missing/invalid Secret, token failure, or outside k8s). `X-Go-Proxy-*` header names are rejected. **A credential is sent only to the hosts its Secret allows**: the Secret must carry `mcp.io/allowed-hosts` (`backendauth.AllowedHostsAnnotation`: comma/space-separated `host` or `host:port`), and `transport.RoundTrip` refuses a request to any other host — so neither a discovery change pointing a server elsewhere (e.g. an admin adding a static server with an attacker URL and someone else's `credentialsSecret`) nor a backend's redirect can carry the credential away; changing the list needs Kubernetes Secret write access, which the `_admin.*` tools don't have. A Secret without the annotation is refused. Secrets are read only in go-proxy's own namespace, and go-proxy may `get` only the ones its discovery config names: `deploy.sh`'s `apply_credentials_rbac` (`scripts/lib/deploy-proxy.sh`) renders the `go-proxy-credentials` Role with exactly those `resourceNames`, from the live `discovery-override` (or the cfg before it's seeded), and deletes it when there are none (an empty `resourceNames` would mean every Secret). A Secret assigned later through `_admin.update_discovery` needs `deploy.sh --deploy-proxy` re-run; until then the read is `Forbidden` and `readKubernetesSecret` fails closed with an error saying so. So `_admin.*` alone can't make go-proxy read a Secret the cluster operator didn't grant. Tests: `backendauth/backendauth_test.go`, `dynamic_proxy/backend_credentials_test.go`, `discover_mcp_servers_test.go`'s `TestParseConfig_StaticMode_CredentialsSecretRoundTrips`.

## Internal identity assertions

Role-based access control (above) can only express "this role may call this tool/prompt/resource at all" — it can't express resource-level ownership (e.g. "role `user` may call `get_account_balance`, but only for the caller's own account"), because only the *backend* knows which account belongs to which user. To let a backend enforce that without go-proxy forwarding the client's own credential:

- **`relayheaders`** is the one place that knows the four `X-Go-Proxy-*` headers this whole mechanism (and "Tool-call correlation ID") is built on: `AssertionHeader` (identity assertion), `RelayTokenHeader` (relay/loopback token), `CallbackURLHeader`, `ToolCallIDHeader`. It isn't `package main`, so any backend can import it directly. `relayheaders.Extract(h)` reads all four off an inbound request into a `Set`; `Set.Apply(h)` puts them on an outbound one. **Backend side:** `Set.Client(base)`/`ClientFor(h, base)` forward the *entire* `Set` extracted from the inbound request verbatim — the standard shape for "relay a call back into the proxy": never pick out individual fields by name (e.g. `relayheaders.Set{Assertion: incoming.Assertion}`), which would silently drop the relay token or any field added later. Every gardening-demo relay does this (`incoming.Client(nil)`). `VerifyAssertion(verifier, h)` verifies the identity assertion. **Proxy side:** `WithMinter(ctx, MintFunc)` + `ServerTransport{Server: name}` — see "Propagation path" below.
- **Never forward the client's original `Authorization` header/JWT to a backend.** It was ruled out deliberately: that token's audience/lifetime is scoped to authenticating *to the proxy*, and leaking it to a backend would hand a compromised backend a live, generally-replayable credential valid wherever that token is trusted. Unsigned forwarded headers were ruled out too — their safety would depend entirely on NetworkPolicy enforcement holding, which isn't guaranteed across every CNI.
- Instead, the proxy mints a **second, short-lived JWT of its own** — `auth.Signer`/`auth.SignerFromKey` (`auth/signer.go`) — signed with an RSA keypair **dedicated to this purpose and never written to disk or git**, distinct from whatever key verifies the external client-facing token (in production that's `demo-authorization-server`'s JWKS endpoint, see "Auth and access control"; in the root package's own tests it's a keypair `mcp_client_test.go`'s `init()` generates fresh every run, see below), asserting only the already-verified `sub`/`role` from the client's own token. The key itself is resolved by `internal_signing_key.go`'s `bootstrapInternalSigningKey` (see the next bullet) rather than read from a path. `auth.Verifier` (used both for the client-facing token and, by backends, for this assertion) already does exactly the RS256-verify-against-a-configured-key-and-issuer/audience job needed; a backend builds its own `auth.Verifier` with `JWKSURL` pointed at the proxy's own `/.well-known/jwks-internal.json` (see below) and `Issuer: auth.DefaultInternalIssuer, Audience: auth.DefaultInternalAudience` — the same `JWKSURL`-based code path `auth.Verifier` already supported for a real external IdP, just pointed at go-proxy itself instead.
- **No PEM file anywhere, in git or on disk — the key is generated and coordinated at runtime.** `internal_signing_key.go`'s `bootstrapInternalSigningKey(ctx)` is called once from `doRunOn` whenever `internalAuth` is configured. Outside k8s (a standalone binary, or any hermetic test — detected the same way every `configsync` caller already detects it, via `configsync.K8sClientset()` returning an error) it just calls `auth.GenerateKey()` and keeps the result in memory: there's only one such process, so there's nothing to coordinate. Inside k8s, every replica must sign with the *same* key (a backend only ever reaches one replica's JWKS endpoint per request, so a replica signing with a key no other replica would ever serve back would mint assertions no backend could reliably verify) — the first replica to start creates the `go-proxy-internal-signing-key` Secret (get-or-create, race resolved by falling back to a `Get` on `AlreadyExists`, the same idiom `configsync`'s own `updateK8s` uses for its ConfigMaps) holding a freshly generated key; every other replica (including this one, on a later restart) reads that same Secret back via `configsync.K8sClientset()`/`configsync.PodNamespace()` (exported specifically so this file can reuse `configsync`'s existing k8s-client/namespace singletons rather than dialing in-cluster config a second time). A fresh keypair is generated only when the Secret doesn't already exist — a rolling restart of existing pods deliberately reuses the same key, since rotating it mid-rollout would invalidate assertions already minted by pods still finishing in-flight requests. `k8s/go-proxy-serviceaccount-rbac.yaml` grants go-proxy's ServiceAccount `get`/`create` (not `update`/`delete`/`list`/`watch`) on `secrets` for exactly this.
- **`/.well-known/jwks-internal.json`** (`runProxyServerOn`, mounted only when `internalSigner != nil`) serves `internalSigner`'s public key as a standard JWKS document via `auth.Signer.JWKSHandler()` (`github.com/MicahParks/jwkset`, `keyfunc`'s own server-side counterpart) — deliberately unauthenticated, like `/healthz` and `/.well-known/oauth-protected-resource`: a backend needs to fetch this before it can verify anything. `Signer.Sign` embeds a `"kid"` JWT header (`Signer.KID()`, a SHA-256 hash of the DER-encoded public key) matching the JWK's own `kid` in this document — required for `keyfunc`'s `Keyfunc` callback to pick the right key. A backend that wants to verify go-proxy's internal identity assertion points its own `-internal-jwks-url` flag at this endpoint (e.g. `http://go-proxy.mcp-proxy.svc.cluster.local/.well-known/jwks-internal.json` in k8s — the same Service DNS shape as `selfUrl`; no currently-deployed backend does — see the next bullet); reachability is already covered by the existing `allow-ingress-to-proxy` NetworkPolicy, which opens ingress on go-proxy's pods from any source on port 8081, not just external clients. The proxy verifies its *own* minted assertions (`relayTokenVerifier`, used when a relay or loopback token comes back — see below) directly from `internalSigner.PublicKey()` via `auth.NewVerifierFromKey`, skipping the JWKS round trip entirely since it already holds the key in memory.
- **Config**: an optional `internalAuth` combined-config section (same nil-if-absent convention as `auth`/`governanceOrchestration` — see `config.go`'s `ProxyConfig.InternalAuth *auth.SignerConfig`), e.g. `{"issuer": "go-proxy", "audience": "go-proxy-backend", "ttlSeconds": 60}` (`ttlSeconds`: 0 for the default 60, at most 3600, since a leaked minted token is usable until it expires) — no key path fields at all; `SignerConfig` only carries the minted-assertion claim shape (issuer/audience/TTL), never key material or a key path. Absent section ⇒ `internalSigner` (the `main.go` package var) stays `nil` ⇒ the whole feature is a total no-op: no assertion is ever minted or attached, so every existing config/test that omits it is completely unaffected.
- **Propagation path — tokens are minted per destination, per request**: `createMiddleware` (`middleware.go`) puts the caller's verified identity on `ctx` as an `auth.Identity` (`sub`, roles, the next hop number, an expiry cap, the tool-call ID, the relay origin) and as a `relayheaders.MintFunc` (`minterFor`, via `relayheaders.WithMinter`) — placed **before** the per-request-kind branches, so tools, prompts, resources and resource templates are covered uniformly. Every session go-proxy opens to a backend has its own `relayheaders.ServerTransport{Server: <name>}` (`session_proxies.go`'s `backendHTTPClientFor`, `triggered-tools-runtime/runtime.go`'s `platformHTTPClientFor`), which on each outbound HTTP request asks the request context's minter for headers **for that server**: an identity assertion (`auth.Signer.SignAssertion`, `aud` = `[<audience>, <audience>/<server>]`) always, and — only if `internalAuth.relay` lists that server and `selfUrl` is set — a relay token (`SignRelay`) plus the callback URL. A minting error fails the request rather than sending it without the caller's identity. The `ctx` reaches the transport unmodified via `next(ctx, method, req)` → the gateway's handler → `sess.CallTool`/`GetPrompt`/`ReadResource` → the go-sdk's `streamableClientConn.Write` (`http.NewRequestWithContext(ctx, ...)`). Don't move minting to a session- or connection-scoped field: cached backend sessions are shared by concurrent callers, so per-request context is what keeps each call's tokens scoped to that call. Discovery pollers carry no minter, so they send no tokens.
- **Verification is opt-in per backend**: no currently-deployed backend in this repo checks the identity assertion; the mechanism is exercised by `internal_auth_test.go`'s in-process "account-service" stand-in, which requires the per-server audience (`go-proxy-backend/account-service`), so an assertion minted for any other backend wouldn't pass. Every backend receives the assertion but most ignore it. A backend that opts in is expected to fail closed. Any backend in this Go module can import `relayheaders`/`auth` to verify it.
- **A resources/read authorization gotcha**: `isResourceRoleAuthorized` (role-based access control) is checked against `allowed_resources`, not `allowed_resource_templates`, for *every* `resources/read` call — including ones that only match via a registered template — because `createMiddleware` can't tell in advance whether a given URI will resolve via an exact `Resource` or a `ResourceTemplate.Matches` (see "Reads (`ReadResource`) have a dispatch nuance the other three kinds don't" (`gateway.md`)). So an access rule meant to allow reading a *template's* matched URIs needs an `allowed_resources` pattern (e.g. `"account-service:*"`), not just `allowed_resource_templates` (which only gates `resources/templates/list` filtering) — getting this wrong denies the request at the role-check layer before it ever reaches the backend's own ownership check, which looks like the internal-assertion mechanism failing when it's actually the access-rules config.
- **Test**: `internal_auth_test.go` (`proxyserver` package) is fully self-contained/hermetic — no PEM files at all, since neither side reads a key from disk. Its `internalAuth` config section is just `{"issuer": "go-proxy", "audience": "go-proxy-backend", "ttlSeconds": 60}`, and its in-process "account-service" stand-in (`get_account_balance` tool + the same resource template, duplicated rather than imported — same `package main` test constraint as `platform_servers_test.go`'s stand-ins) on port `:8095` is built around an `internalVerifierHolder` (mutex-guarded `*auth.Verifier` pointer) rather than a `*auth.Verifier` passed in directly at construction: the real verifier can only be built (via `JWKSURL` pointed at `http://localhost:8096/.well-known/jwks-internal.json`) *after* the proxy (`doRunOn` on `:8096`, the next free port after `platform_servers_test.go`'s `:8091`–`:8094`) has actually started and is serving that endpoint, but the backend's own listener starts earlier (so discovery isn't held up waiting on the proxy) — `verifierHolder.set` is called once, right after `startTestProxy` returns, before any client call happens. Scenarios: Alice's own account succeeds (tool call and resource read both), Alice's call/read for Bob's account is denied by the *backend's* ownership check (not go-proxy's role check, which already allows `user` to call `account-service.*` generally), and a request forged with a *different*, independently-generated keypair — sent directly to the in-process backend, bypassing the proxy entirely — is denied, proving the backend actually verifies the signature (against the key it fetched from the real JWKS endpoint) rather than just checking the header is present. `proxyserver/testdata/integration_test.cfg` has no `internalAuth` section, so `TestProxyClient` runs with `internalSigner == nil`.
- **Relaying — a backend calling back into the proxy as the user — needs a relay token, and only configured backends get one.** The identity assertion is **never** a credential: `authenticateRequest` doesn't accept `X-Go-Proxy-Assertion` at all (its audience isn't one the proxy accepts), which is what stops a malicious or compromised backend from turning "this is who called me" into "act as them" — including for an admin. Instead, `internalAuth.relay` (startup-only, `auth.SignerConfig.Relay`; validated by `config.go`'s `validateInternalAuth`) lists, per backend server name, the tools/prompts/resources (`GlobMatch` patterns) it may relay to; only those servers receive `X-Go-Proxy-Relay-Token` + `X-Go-Proxy-Callback-URL`. A relay token (`aud` `go-proxy-relay`) carries `relay_from` (the server it was sent to), `hop`, `tcid` and an `exp` that's never later than the credential the original request arrived with. On the way back in, `relayAuthFromClaims` checks: exactly one accepted audience, `hop ≤ internalAuth.maxRelayHops` (default 3), and that `relay_from` may relay; then `checkRelayTarget` allows only that server's targets (list methods and protocol methods are allowed and still role-filtered) and **never `_admin.*`**, whatever the patterns say; then the ordinary role checks apply as for a direct call. So a relayed call can never exceed the original caller's authority, can only reach what its backend is configured for, can't be renewed past the original credential's expiry, and can't loop forever. `internalAuth` isn't a configsync section, so `_admin.*` tools can't widen relay permissions — the same reasoning as `roleMapping`. Relay permissions are keyed by server name, so the shipped cfgs also pin every relaying server in `discovery.k8sPinnedServers` (see `discovery.md`).
- **The proxy's own loopback (`proxy_utility.call_tool`/`render_prompt`) uses a loopback token** (`aud` `go-proxy-loopback`, `SignLoopback`, `utility_tools.go`'s `loopbackHeaders`), sent only to `selfUrl`, never to a backend — so it keeps the caller's full authority, including `_admin.*` for an administrator. Its `hop` makes nested `call_tool` stop at `maxRelayHops`. If the request handling `call_tool` is itself part of a backend's relay, the loopback token keeps that `relay_from`, so the relay's restrictions (targets, no `_admin.*`) follow the call through `call_tool`.
- **Two authentication paths, not more**: presence of a client `Authorization` header always selects the ordinary path, even if it turns out invalid — it never falls back to a relay token, which would otherwise be a downgrade vector (present a broken client token alongside a forged relay header, hoping for a fallback). Only when `Authorization` is *absent* does it check `relayheaders.RelayTokenHeader`, verified with `relayTokenVerifier` (signature, issuer, expiry; audience checked by `relayAuthFromClaims`). Neither header present ⇒ rejected; an identity assertion alone ⇒ rejected, with a message saying it isn't a credential.
- **Test**: `backend_relay_test.go`'s `TestBackendRelay` captures real tokens from a forwarded call (via an echoing backend) and presents them straight back: the identity assertion is rejected (also an admin's, at `_admin.*`); a non-relaying backend gets no relay token or callback URL; the relay token works for an allowed target and keeps the tool-call ID; it's refused beyond the user's role, outside the server's targets, at `_admin.*`, through `call_tool` to `_admin.*` or a non-target, past `maxRelayHops`, when expired, and from a server not allowed to relay; the next hop's tokens don't outlive the first. `TestAuthenticateRequestRelayTokens` checks each refusal's reason, `TestCheckRelayTargetNeverAllowsAdmin` the `_admin.*` rule. `utility_tools_test.go` covers an admin's `call_tool` reaching `_admin.*` and nested `call_tool` stopping at the hop limit.

## Tool-call correlation ID

Every `tools/call` gets a UUID (`github.com/google/uuid`) that's threaded through everything that call causes, so the whole causal chain — the real backend call, any triggered-tool calls an orchestration runs around it, and every event it produces — can be correlated by one ID.

- **Minted or reused, never duplicated, never client-chosen**: `createMiddleware` (`middleware.go`), for a `*mcp.CallToolRequest` (before the role check, so even a role-rejected call gets logged with one), reuses the tool-call ID carried in a verified relay/loopback token's `tcid` claim, and otherwise mints a fresh `uuid.NewString()`. A client-supplied `X-Go-Proxy-Tool-Call-Id` header is ignored — a client could otherwise forge or reuse another call's ID in audit events. The resolved ID goes into the `auth.Identity` on `ctx`, so every token minted for the call carries it.
- **Propagation to backends and relayed calls**: `relayheaders.ToolCallIDHeader` is sent to every backend (informational), alongside the assertion; the relay token carries the same ID in `tcid`, so a relaying backend that forwards its whole `Set` keeps the call correlated without doing anything else.
- **Propagation to triggered-tool calls is an explicit field, not *solely* a header**: `triggered_tools_runtime.Runtime`'s session cache (`runtime.go`'s `platformHTTPClientFor`) attaches the same per-server relay headers an ordinary backend call gets (see "Triggered tools / orchestration" (`orchestration.md`)) — but `ToolCallID` is also an explicit `CallAuthorizationInput`/`ResultAuthorizationInput` struct field (`contract.go`): it's the only source at all for a **native** step (never goes over the wire, so there's no header to read) and remains the authoritative value even for a discovered step. `Runtime.Guard` (`orchestrate.go`) takes an explicit `toolCallID string` parameter (threaded from `createMiddleware`'s call site) and populates it on every call/result-authorization invocation and on `fireAudit`'s published event. Since a triggered tool's handler (e.g. `platform_servers_test.go`'s in-process `authorization-mcp-server` stand-in — see "Triggered tools / orchestration" (`orchestration.md`)) uses these structs directly for its typed handler, the field flows into each tool's discovered `InputSchema` automatically — `validate.go`'s property-name-set check (derived from the same structs via `jsonschema.For`) can't drift out of sync with it.
- **Mandatory event metadata**: `ToolRequestResultEvent` (`event_publisher.go`) has a `ToolCallID` field; `main.go`'s `publishToolRequestResult` sets it as the `"toolCallId"` metadata key on every `tool-request-result` event. The `authorization-mcp-server` stand-in's `publishAlert` does the same for `alert` events, from the `ToolCallID` on whichever `CallAuthorizationInput`/`ResultAuthorizationInput` triggered the rejection. `"toolCallId"` is a `required: true` string key on every event type in every copy of the event dictionary that must stay in sync (`proxyserver/testdata/event_dictionary_test.json`, `proxy-server.cfg`'s and `proxyserver/testdata/orchestration_test.cfg`'s inline `eventDictionary` sections — see "Configuration sync (configsync)" (`configsync.md`)) — `events.Dictionary.Validate` fails closed on a missing required key, so a stale copy of the dictionary breaks event publishing outright rather than silently dropping the field.
- **Test**: `backend_relay_test.go`'s `TestBackendRelay` covers a direct call getting a minted ID, two independent direct calls getting distinct IDs, a client's forged `X-Go-Proxy-Tool-Call-Id` being ignored, and a relayed call keeping the original ID from its token. `event_system_test.go`'s `TestEventSystem` and `platform_servers_test.go`'s `TestPlatformServersOrchestration` both assert a call's `alert`/`tool-request-result` events carry a non-empty, matching `toolCallId`, and that independent calls get distinct ones. `relayheaders/relayheaders_test.go` covers `Extract`/`Apply`/`Empty`, `ServerTransport` minting per server (and failing on a mint error), and `VerifyAssertion`'s fail-closed cases.
- **Client token checks to set**: `auth.issuer` and `auth.audience` are each enforced only when set (`auth_service.go`'s `parserOptions`). go-proxy logs a warning at startup for each one that's empty: without an audience, any token the IdP signs is accepted, which on a shared tenant (Okta, Entra ID, Auth0) means tokens issued for every other application there.
- **CLI login (`oauthclient`)**: the loopback `/callback` checks `state` before anything else, so a request without this login's state (any local page or process can send one) is answered and ignored rather than able to end the login; only the first real callback is used. `DiscoverMetadata` requires the metadata's `issuer` to be the server it asked (RFC 8414 §3.3), against authorization-server mix-up - or, for a server reached at another address than its issuer, the issuer named explicitly (`LoginOptions.Issuer`, the CLIs' `-auth-issuer`): the gardening seed Job reaches demo-authorization-server through its in-cluster Service while its issuer stays `http://localhost:8102`. Tests: `login_test.go`'s `TestLoginIgnoresForgedCallback`, `TestDiscoverMetadataRefusesOtherIssuer`.
- **Logs**: debug-level request and result logging (`createMiddleware`, `mcptrace`) records sizes (`logging.Size`), never argument or result values, since debug can be switched on cluster-wide at runtime; `natsUrl` is logged with any password masked (`logging.URL`). `backendauth.Store` re-reads a Secret without holding its lock, serving the last good credential to other callers meanwhile.
