# Build, deploy, and local cluster

> Cross-references to sections elsewhere name their file; see `README.md` for the index.

## Build and deploy

Deploying to the local k3s cluster is two separate steps, each its own script: `./scripts/build.sh` builds every docker image (tag `:local`, still consumed directly by Colima/k3s's own containerd — no registry involved) and this repo's two CLI binaries (`bin/cli`, `go-gardening-demo/bin/cli`); `./scripts/deploy.sh` only applies/updates k8s state (namespaces, RBAC, NetworkPolicies, ConfigMaps/Secrets, Deployments/Services, scale/rollout) and never builds anything — it fails fast via `require_image` (a `docker image inspect <name>:local` check) with a message pointing back at `./scripts/build.sh` if an image it needs isn't present yet. (This is the default, local-daemon path; `./scripts/build.sh --release`/`./scripts/deploy.sh --release` below is the alternate path for publishing to, and deploying from, a private GHCR package — usable against any cluster, not just this one.)

Both scripts are thin wrappers around one root `Makefile`, which is where the actual incremental-build logic lives: each of the 12 docker-buildable targets (go-proxy plus every `platform-mcp-servers/*`/`ai-mcp-servers/*`/`go-gardening-demo/servers/*`/`demo-authorization-server` folder, plus `gardening-demo-seed` — see "In-cluster gardening-demo seeding") and both CLI binaries gets a `.build/<name>.image.stamp` (or, for the CLIs, the binary itself) as its Make target, only rebuilt when something it actually depends on changed. Each target's Dockerfile defaults to the shared root `Dockerfile` (`DOCKERFILE_$(1) ?= Dockerfile` in `DOCKER_IMAGE_RULE`) but can be overridden per target — `gardening-demo-seed` is the one exception, using its own `go-gardening-demo/seed/Dockerfile` since it also needs to bundle `go-gardening-demo/initial-data/` (1.6MB, over a ConfigMap's 1MiB limit) into its image, which the shared Dockerfile has no mechanism for; its own `EXTRA_DEPS_$(1)` additionally tracks that data's own files for staleness, since they aren't Go source `DEPS_$(1)_FILES` would ever notice changed. Staleness is **not** a naive per-directory mtime check — this is one Go module with heavy shared-package reuse, so a directory-only check would miss a shared-package edit entirely. Instead each target's true transitive dependency set is computed via `go list -deps -e -f '{{if not .Standard}}{{.Dir}}{{end}}' ./<BUILD_PATH>` (filtered to in-repo paths), turned into `$(wildcard <dir>/*.go)` prerequisites. Concretely: `go-gardening-demo/servers/garden-business-ops` looks self-contained by directory, but actually transitively imports `access_control`, `auth`, `dynamic_proxy`, `relayheaders`, and `triggered-tools-runtime` — editing any of those correctly triggers a rebuild of its image, editing an unrelated server does not. `./scripts/build.sh --build-server PATH` (mirroring `deploy.sh`'s own `--deploy-server PATH`) gets the identical treatment for an arbitrary folder via a make-variable-triggered rule instantiation (`ADHOC_NAME`/`ADHOC_BUILD_PATH`), so `require_image`'s check works the same regardless of how an image was built. `./scripts/build.sh` takes no target-selection flags otherwise — since staleness is tracked correctly, building everything is a cheap, side-effect-free, idempotent default (unlike `deploy.sh`'s flags, which gate real cluster mutations like pod restarts and stay deliberate/explicit); `./scripts/build.sh --clean` wipes `.build/`/`bin/`/`go-gardening-demo/bin/` to force a from-scratch rebuild.

**Publishing a release (`./scripts/build.sh --release VERSION`)** pushes every one of the 12 images to a GHCR package (`ghcr.io/<owner>/<name>:VERSION`; the scripts assume it may be private, so pulls authenticate with a token) so a deploy-only machine — no local build, no Colima — can consume them against a cluster of its own; the local `:local` tag/daemon-only flow above is completely unaffected, publishing is additive. `--release` requires `--github-token-file PATH` (a GitHub PAT with `write:packages`+`read:packages`; `--github-owner NAME` defaults to whatever `git remote get-url origin` resolves to), a clean working tree, and either creates+pushes a git tag named `VERSION` at HEAD or (idempotently) confirms one already points there — a tag pointing at a *different* commit is a hard error, since a version name is meant to be a stable, reproducible pointer. Every image is tagged+pushed **regardless of whether it needed a rebuild this particular run** (`Makefile`'s `publish-$(1)`/`publish-all`, decoupled from the staleness-gated `image-$(1)` build step it depends on): if only rebuilt images were pushed, a version tag could be incomplete — any image that hadn't changed since some earlier version simply wouldn't have this tag at all, so a deployer asking for that version would hit a hard `require_ghcr_image` failure for it. Decoupling rebuild-staleness from publish-completeness establishes a real invariant instead: *any version visible in GHCR has all 12 images under it.*

**Docker images are architecture-locked to whichever machine runs `build.sh --release`** — `docker build` with no `--platform`/buildx involved always produces an image matching the host's own native architecture, unlike the CLI binaries in the deploy-bundle tarballs below (cross-compiled explicitly via `GOOS`/`GOARCH`, so they're correct regardless of host arch). `build.sh` detects the host's arch (`go env GOARCH`) and, on `amd64`, transparently republishes under `VERSION.amd64` instead of `VERSION` — a distinct GHCR tag, git tag, and GitHub Release, with `darwin/amd64`+`linux/amd64` tarballs instead of the `arm64` pair — so an amd64 build and an arm64 build of what's nominally "the same version" can never silently clobber each other's images under one shared tag. A deployer picks whichever matches their own cluster/target: `--release VERSION` for an arm64 one, `--release VERSION.amd64` for an amd64 one. Building on a host that's neither `arm64` nor `amd64` is a hard error for `--release` (plain, no-`--release` builds are unaffected either way — this only matters once images actually get published).

**Script layout (`scripts/lib/`)**: `scripts/deploy.sh` holds only the interface and orchestration — flag defaults, `usage()`, option parsing, every validation, the GHCR login, and the main flow. Every function it calls lives in a **sourced** library under `scripts/lib/`: `common.sh` (the three namespace names and `MANAGED_NAMESPACES`, `DEMO_AUTH_PORT`, the claude-bridge `/tmp` paths, `github_owner_from_url`/`github_repo_from_url`), `images.sh` (local/GHCR image checks, the pull Secret, `apply_ghcr_release`), `k8s.sh` (namespaces, `apply_ingress_overlay` and its `proxy_ingress_tls_secret` helper, LoadBalancer polling), and one file per deploy target — `deploy-proxy.sh`, `deploy-auth.sh`, `deploy-gardening-demo.sh`, `deploy-servers.sh` (`deploy_folder`/`deploy_category`, AI tools, claude-bridge). They're sourced, not executed, deliberately: the functions read the global state option parsing sets (`FROM_GIT_PACKAGE`, `INGRESS_HOST`, `DEMO_PASSWORD`, …), which separate executables couldn't see without threading every value through. Rules for a lib file: `# shellcheck shell=bash` header naming what it holds and which globals it reads; no `set` options of its own (it inherits the caller's `set -euo pipefail`); no top-level side effects beyond defining constants and functions; sourced by absolute path after `REPO_ROOT` is set. `build.sh`, `cleanup-k8s-cluster.sh` and `observe-k8s.sh` source `common.sh` too, so a namespace name or the GitHub-remote parsing exists exactly once. `scripts/lib` must stay in `build.sh`'s `BUNDLE_PATHS` (see "Deploy-bundle tarballs" below), or a bundled `deploy.sh` fails at its first `source`.

**Deploying a release (`./scripts/deploy.sh --release VERSION`)** pulls from that same GHCR package into whichever cluster `kubectl` is currently configured against — not necessarily this repo's own local Colima/k3s. There's no separate `--fromGitPackage`/`-fg` flag: passing `--release` at all is what selects this path (internally tracked as `FROM_GIT_PACKAGE`, derived from whether `--release` was given). `--release` is mandatory for it, with **no auto-detection** from a git tag or an embedded `VERSION` file — the version is always stated explicitly, since a commit or tarball could plausibly carry more than one published version (e.g. an arch-specific suffix), making any guess ambiguous. Requires `--github-token-file`/`--github-owner` (same conventions as `build.sh`), creates a `ghcr-pull-secret` (`kubernetes.io/dockerconfigjson`) in every namespace it touches, and — instead of `require_image`'s local `docker image inspect` check — uses `require_ghcr_image` (`docker manifest inspect`) plus `apply_ghcr_release(namespace, name, kind, manifest_files...)`, which renders a throwaway Kustomize overlay over the unmodified manifest files (rewriting the image to the GHCR reference and adding the pull secret) and applies the fully-substituted result in one shot — no checked-in `deployment.yaml` is ever edited, and unlike a live `kubectl patch`/`kubectl set image` pair, the object is never briefly created with the wrong image, since Kustomize computes the final manifest client-side before `kubectl` ever sees it (this requires each `$kind` object's container name to equal its own name, true for every manifest in this repo). `$kind` is `Deployment` at both of its original call sites; see "In-cluster gardening-demo seeding" for its `Job` use. Incompatible with `--use-headless-claude` (host-only dev tooling, meaningless against a published image).

**Generic-cluster deploy support**: everything below is gated on `--release` — the default local Colima/k3s flow is unaffected. One of this repo's assumptions only holds for the local cluster and would otherwise hang and hard-fail the whole script under `set -euo pipefail`: `deploy_proxy_workload`'s/`deploy_auth_server`'s wait on a k3s klipper `svclb-*` pod (a label that simply doesn't exist on any other cluster) is replaced by `poll_service_loadbalancer_address`, a bounded, non-fatal poll of the Service's own `status.loadBalancer.ingress` instead. The final "reachable at" message similarly queries the Service's actual assigned address when `--release` was given, rather than assuming `localhost`.

**Ingress exposure (`--ingress-host`)**: opt-in enterprise path (operator guide: `docs/enterprise-deployment/enterprise-deployment.md`). Without the flag nothing changes — `k8s/go-proxy-service.yaml` stays a LoadBalancer and `deploy_proxy_workload` applies it exactly as before. With it, `apply_ingress_overlay` (`scripts/lib/k8s.sh`; generic in namespace/name/overlay directory, though go-proxy is its only user) renders go-proxy's Deployment/Service plus `k8s/overlays/ingress/` through a scratch Kustomize overlay (same render-then-pipe/`--load-restrictor` mechanism as `apply_ghcr_release`, duplicating its image/pull-secret overrides under `--release`): the Service is patched to `ClusterIP` (`service-clusterip-patch.yaml`), and `ingress.yaml` is added with its `__INGRESS_HOST__`/`__INGRESS_CLASS__` placeholders substituted by `sed` and a `spec.tls` patch whenever `proxy_ingress_tls_secret` names a Secret (`--tls-secret`, else `go-proxy-tls` with `--cluster-issuer`). `--cluster-issuer NAME` (only with `--ingress-host`) additionally adds the `cert-manager.io/cluster-issuer` annotation, so cert-manager issues and renews that Secret, plus `k8s/overlays/networkpolicy-acme-http01-solver.yaml`: cert-manager's HTTP-01 solver pod runs in the Certificate's own default-deny namespace and would otherwise be unreachable. Before anything is applied, with `--deploy-proxy` the `--config` cfg's `auth.resourceUrl` must equal the URL this run publishes (`https://HOST/mcp` with TLS, else `http://`), or `deploy.sh` fails fast. Every LoadBalancer wait (klipper `svclb-*`, `poll_service_loadbalancer_address`) is skipped on this path. `k8s/overlays/` is never picked up by `deploy_proxy`'s `k8s/*.yaml` glob (top-level only). `proxy-server.okta.cfg.example` and `docs/enterprise-deployment.md` ship in the deploy-bundle.

**In-cluster gardening-demo seeding**: go-gardening-demo data seeding runs as a one-shot in-cluster Job (`gardening-demo-seed`), unifying the local and `--release` paths — there is no host-side `cli init` step in either mode. `scripts/deploy.sh`'s `seed_gardening_demo_if_needed` checks whether a Job named `gardening-demo-seed` already exists in the `gardening-demo` namespace (the same "a `Get` that finds the object already exists is a no-op" idiom this repo already uses for ConfigMaps/Secrets — see "Configuration sync (configsync)" (`configsync.md`)) and only creates it the first time — a Job's `.spec.template` is immutable, so re-applying an existing one after a new `--release` changed its image tag would fail outright, and reseeding on every redeploy isn't desirable anyway (every `load_*` handler upserts by ID, so it's data-safe but would silently clobber live demo-data edits). Its image (`ghcr.io/<owner>/gardening-demo-seed:<version>` when `--release` was given, `gardening-demo-seed:local` otherwise) bundles the compiled `go-gardening-demo/cli` binary plus `go-gardening-demo/initial-data/` (see `go-gardening-demo/seed/Dockerfile`), and its `args` run the same `cli ... init -data-dir ...` invocation `go-gardening-demo/cli.sh` would, using go-proxy's and demo-authorization-server's in-cluster Service DNS addresses (`http://go-proxy.mcp-proxy.svc.cluster.local/mcp`, the same address `proxy-server.cfg`'s own `selfUrl` uses; `$AUTH_SERVER_URL`, defaulting to `http://demo-authorization-server.demo-auth.svc.cluster.local:8102`) instead of `localhost` — reachable identically on any cluster, not just this repo's Colima/k3s setup, with no NetworkPolicy changes needed (`gardening-demo`'s namespace only restricts *ingress*, not egress). `apply_ghcr_release` (above) was generalized to take a `kind` parameter (`Deployment` at its 2 existing call sites, `Job` for this one) rather than duplicating its Kustomize-overlay body, since a Job's pod-template nesting is identical to a Deployment's. **To reseed deliberately**, the pre-existing `go-gardening-demo/cli.sh ... init` path is unchanged and still the documented way to do it on demand; **to make a future automatic deploy reseed again**, delete the Job first: `kubectl delete job gardening-demo-seed -n gardening-demo`. Before logging in, the Job's container waits up to 60 s for demo-authorization-server to answer it: the IdP's NetworkPolicy admits the Job's pods by label, and on a fresh cluster the network plugin can take a few seconds to apply that to a brand-new pod, refusing the connection meanwhile. It passes `-auth-issuer=http://localhost:8102`, the IdP's fixed issuer, since it reaches the IdP at its in-cluster address.

**What a deployer targeting a different cluster might still need to change, and how** — goal is no yaml edits in the common case:
- `selfUrl` (`proxy-server.cfg`) needs no deployer action: `http://go-proxy.mcp-proxy.svc.cluster.local/mcp` is already portable, since go-proxy's own namespace/Service name are fixed constants in `deploy.sh` and `svc.cluster.local` is the standard cluster-DNS suffix on virtually every distribution. Only a cluster with a customized `--cluster-domain` (rare) would need this changed.
- **go-proxy's own API access is by name** (`k8s/go-proxy-serviceaccount-rbac.yaml`): `get`/`update` on its eight `<section>-override` ConfigMaps, `get` on the `go-proxy-internal-signing-key` Secret, and `create` on ConfigMaps and Secrets (seeding them; RBAC can't scope `create` by name, and creating gives no access to existing objects). No `list`/`watch`, and no access to `proxy-server-config` (go-proxy reads it as a mounted file; only `deploy.sh` writes it, so the startup-only `auth`/`roleMapping`/`internalAuth` can't be changed from inside go-proxy), the NATS Secrets, the pull secret or the AI key. Backend credentials Secrets get their own rendered Role (`apply_credentials_rbac`, see `auth.md`); Service discovery its per-namespace one (`apply_discovery_rbac`, see `discovery.md`). `proxyserver/config_drift_test.go`'s `TestRBACCoversEveryLiveSection` keeps the ConfigMap names in step with the configsync sections.
- **LoadBalancer only where it means localhost.** `k8s/go-proxy-service.yaml` and `demo-authorization-server/k8s/service.yaml` are `ClusterIP`. `deploy.sh` sets `LOCAL_CLUSTER` (a local build always targets the local cluster; a `--release` deploy is local when `cluster_is_local` finds the kubeconfig's API server on a loopback address, as with Colima, kind or k3d, or at Docker Desktop's `kubernetes.docker.internal`; minikube's VM address counts as remote) and `expose_on_local_cluster` (`scripts/lib/k8s.sh`) patches both Services to `LoadBalancer` there. On any other cluster go-proxy stays `ClusterIP` unless `--public-load-balancer` (a cloud LoadBalancer is a public address, serving plain HTTP), and demo-authorization-server always does — it hands an admin token to anyone who logs in as `admin`/`admin`. The end-of-deploy message prints port-forward and `--ingress-host` instructions when go-proxy isn't a LoadBalancer. A `--release` deploy that includes the demo auth server, or whose config trusts it, prints a warning that the demo login is for demos only.
- Default StorageClass (`platform-mcp-servers/event-aggregator/k8s/pvc.yaml` sets no `storageClassName`): present on essentially every managed cluster; if a bare cluster lacks one (`kubectl get storageclass`), either install a provisioner or add an explicit `storageClassName` to that one file.
- NetworkPolicy enforcement (this repo's several `k8s/networkpolicy-*.yaml`) requires a CNI that actually enforces them (Calico, Cilium, most managed defaults) — on one that doesn't (plain flannel), they silently become no-ops; the deploy still works, just without that isolation. No yaml change either way.
- **Policies `deploy.sh` applies**: namespace-wide default-deny plus allow-from-go-proxy ingress in `mcp-proxy`, `gardening-demo` and `demo-auth`; per-Deployment `allow-only-go-proxy-to-<name>` policies for backends deployed into any other namespace (`isolate_backend`); a warning for an unprotected discovery namespace (`warn_if_unprotected`). demo-authorization-server's ingress (`demo-authorization-server/k8s/networkpolicy.yaml`) admits only go-proxy (JWKS), garden-customer-admin/garden-staff-admin (registering demo users), the seed Job, and k3s's ServiceLB pod for its Service, which is how `localhost:8102` logins arrive on a local cluster; on a remote cluster people reach it with `kubectl port-forward`, which NetworkPolicies don't apply to. Opt-in `--egress-policies` adds `go-proxy-egress` (`apply_egress_policy`, rendered from the effective config at deploy time; see the enterprise guide §9.2); without the flag an existing one is removed.

**Deploy-bundle tarballs (no git, no Go toolchain)**: a deployer "is not supposed to compile the CLI Go programs" (`bin/cli`, `go-gardening-demo/bin/cli`), so the documented deployer workflow doesn't require `git clone`-ing this repo and installing Go just to get them. `./scripts/build.sh --release VERSION` additionally packages, for each platform in its `RELEASE_PLATFORMS` list (today `darwin/arm64` and `linux/arm64` — the deployer's *own machine* architecture, i.e. where they'll run `deploy.sh`/`cli` *from*, not the k8s cluster's node architecture, which is a separate, unrelated, already-deferred concern; macOS can't execute a Linux ELF binary at all — which is why this list must track the deployer's real OS rather than assume one), a `deploy-bundle-VERSION-GOOS-GOARCH.tar.gz` containing `scripts/deploy.sh`/`cli.sh`/`cleanup-k8s-cluster.sh`/`observe-k8s.sh` + every `k8s/` manifest directory this repo has + `proxy-server.cfg` + `go-gardening-demo/initial-data` + `examples/discovery` (the hello-world discovery example — no build needed, so it runs from a bundle as-is) + freshly cross-compiled `bin/cli`/`go-gardening-demo/bin/cli` + a plain-text `VERSION` file — no Go source, no `go.mod`, no Makefile, no Dockerfile. It's uploaded as a GitHub Release asset on the same git tag `--release` already creates, via the GitHub REST API directly (`curl`+`python3`, no `gh` CLI) — this requires the token file to additionally carry `repo` scope (beyond `write:packages`/`read:packages`). The bundle is built with `git archive HEAD` from those paths, never copied from the working tree, so a file git ignores (a key, a local cfg) sitting in one of those directories can't reach a public release asset.

**Keeping secrets off command lines and out of builds**: `build.sh --release` passes the GitHub token to `curl` in a header file (`-H @file`, in its 0700 scratch directory, removed by an `EXIT` trap), and `ensure_ghcr_pull_secret` (`scripts/lib/images.sh`) builds the pull secret's `.dockerconfigjson` in a 0600 temp file for `kubectl --from-file`, rather than putting the token in `--docker-password`: any local user can read another process's command line. `ensure_nats_secrets` removes its temp directory (CA and server keys, every NATS password) through an `EXIT` trap, even when a step fails. `.gitignore` ignores secret material by common name anywhere (`*-key.txt`, `*token*.txt`, `*.key`, `*.pem`, `*.p12`, `*.pfx`, `.env*`), and `.dockerignore` keeps the same files, plus `.claude/` and local build output, out of the image build context: `COPY . .` would put them in the build stage's layers and cache, though the final images hold only the binary.

**Warnings rather than prompts**: `deploy.sh` and `cleanup-k8s-cluster.sh` print the kubectl context they're about to change before doing anything, and `deploy.sh --ingress-host` without `--tls-secret`/`--cluster-issuer` warns that go-proxy would be published over plain HTTP.

`scripts/deploy.sh --release`, when run from an extracted tarball (detected via the absence of a `.git` directory at its own `REPO_ROOT`, tracked in `$HAS_GIT_REPO`), requires `--github-owner` explicitly instead of inferring it from `git remote get-url origin` (there's no git remote to ask) — `--release VERSION` itself is required either way, from a tarball or a full git checkout alike, with no auto-detection shortcut for either (see the previous bullet). The tarball still embeds a plain-text `VERSION` file at its root (written by `build.sh`), but it's informational only — nothing in `deploy.sh` reads it. `deploy_folder()`'s `main.go` existence check is gated on the local-build (`:local`) path only, since a tarball ships no Go source.

**Fetching the tarball**: the simplest path is a **plain browser download** — `build.sh --release` prints the Release page URL (`github.com/<owner>/<repo>/releases/tag/<version>`). For a public repo anyone can download the asset there; for a private one, a browser logged in as a user with access lets GitHub serve it directly through that session, no token needed. The scripted, token-based fetch (looking up the release by tag via the API, finding the matching platform asset's `url` field — not `browser_download_url`, which only works unauthenticated on a public repo — and `GET`-ing it with `Accept: application/octet-stream` to follow GitHub's redirect to the actual blob) is not implemented yet; it's the path to add once a deployer needs this scripted against a private repo.


**NATS credentials and TLS (`deploy_proxy`'s `ensure_nats_secrets`, `scripts/lib/deploy-proxy.sh`).** Before applying NATS, `deploy_proxy` creates in `mcp-proxy`, once each: `nats-tls` (a private CA and NATS's server certificate, made with `openssl`; the CA key is discarded after signing), and `nats-client-<component>` for every entry in `NATS_COMPONENTS` (a random password, plus the CA certificate). It then renders `nats-server-config` from `k8s/nats/nats.conf.tmpl` and patches a hash of it onto the NATS pod template, so NATS restarts exactly when its config changes. Redeploys keep every existing password and certificate. To rotate, delete `nats-tls` and/or the `nats-client-*` Secrets and redeploy everything (`--deploy-all`), so each component picks up its new Secret. See "NATS authentication and TLS" in `events.md`.

## k3s/Colima requirements

The default (non-`--release`) local flow targets a reference dev setup: macOS with [Colima](https://github.com/abiosoft/colima) running k3s (`colima start --kubernetes --k3s-arg=--disable=traefik`). Other local clusters work through the `--release` path or with small adjustments described in "Build and deploy".

On a local cluster, `deploy.sh` makes `k8s/go-proxy-service.yaml` a `type: LoadBalancer` on `port: 80` (not `NodePort`) specifically so its URL is both **stable** across redeploys and has **no port number** in it (`http://localhost/mcp` — `:80` is HTTP's default port, so it's never written). This depends on two things about the local Colima/k3s setup, both true by default and neither requiring any new installation:

- **k3s's built-in ServiceLB ("klipper") must be enabled** — it is, by default; only `--disable=traefik` is passed to k3s (Colima's `kubernetes.k3sArgs`), and ServiceLB is deliberately left alone. ServiceLB is what makes `type: LoadBalancer` work at all on a bare k3s node: for each such Service it creates a small proxy pod (named `svclb-<service>-*`, in **`kube-system`**, labeled `svccontroller.k3s.cattle.io/svcname=<service>`/`svccontroller.k3s.cattle.io/svcnamespace=<namespace>`) that binds the Service's `port` directly on the node via `hostNetwork: true` — unlike `NodePort`, this isn't restricted to the 30000–32767 range, which is what lets `port: 80` be used at all. `scripts/deploy.sh`'s `deploy_proxy` (triggered by `--deploy-proxy`/`--deploy-all`) waits on this pod's readiness (in `kube-system`, not the app namespace) before declaring the deploy done.
- **Colima's networking must auto-forward VM-listening ports to the Mac host's `localhost`** — true by default for the `network.address: false` / `mode: shared` config Colima uses by default (see the profile's `colima.yaml`). Nothing extra is configured for port 80 specifically.

One real host-level caveat: if something else on the Mac is already bound to port 80, Colima's forward will fail — this is outside k8s's control and would need to be resolved on the host (e.g. stop whatever else owns port 80) rather than worked around in-cluster.

`cli`'s default `-endpoint` (`http://localhost/mcp`) targets this k8s deployment. A locally-run standalone `./go-proxy` binary is unaffected by any of this — it still listens on `:8081` directly (see `main.go`'s `runProxyServerOn`/`doRunOn` default `addr`) — so reaching one requires passing `-endpoint http://localhost:8081/mcp` explicitly.

`cli` (`cli/`, launched via `./scripts/cli.sh [flags] [<command> [-flag value...]]`) authenticates once, then either runs one command and exits (scriptable mode, if a command is given on argv) or drops into an interactive REPL — one command per line, up/down-arrow history within the session via `github.com/chzyer/readline`, `exit`/`quit` to leave — matching `go-gardening-demo/cli`'s own one-login/many-commands shape (`go-gardening-demo/cli/repl.go`'s `tokenize`/`runREPL` are duplicated verbatim into `cli/repl.go`, same "package main can't cross-import another package main" constraint as everywhere else in this repo), but keeping this tool's own flat command set (`list-tools`, `call-tool`, `load-events`, ...) unchanged rather than adopting that CLI's `<section> <tool>` hierarchy. `cli/dispatch` always returns an error rather than exiting the process — only `main()` (one-shot) or `runREPL` (interactive) decides whether a given error is fatal, so one bad command never kills an interactive session.
