# Triggered tools / orchestration

> Cross-references to sections elsewhere name their file; see `README.md` for the index.

## Triggered tools / orchestration

Go package `triggered_tools_runtime` at `triggered-tools-runtime/` (import path `github.com/pellucon/enterprise-go-mcp-proxy/triggered-tools-runtime`) implements tool-call guardrails via **triggered tools**: individual tools — not whole servers — whose invocation is reserved for the proxy's own orchestration engine, never exposed to end clients. Any MCP server (in this repo, an ordinary `platform-mcp-servers/*` entry, or one of `go-gardening-demo/servers/*`) can freely mix triggered and non-triggered tools side by side; what makes a given tool "triggered" is solely a `_meta` annotation it carries (`triggered_tools_runtime.TriggeredToolMetaKey`, i.e. the JSON key `"go-proxy.triggered-tool"` set to `true` — see `meta.go`'s `IsTriggeredTool`), not which server or directory it happens to live in (`platform-mcp-servers/` groups NATS/orchestration-infrastructure servers by convention, but hiding itself is purely the `_meta` mechanism — see "AI-powered tool discovery" (`utility-and-ai-tools.md`) for a server directory following the same "no special-casing by path" rule). Three fixed phases, but only two are invoked MCP-tool contracts (`triggered-tools-runtime/contract.go`): `call-authorization` (decide before the real call runs), `result-authorization` (decide before the real result is returned). The third, `tool-call-audit`, invokes no tool at all — it's a publish-or-not switch that, when present, makes `Runtime.Guard` publish a `tool-request-result` NATS event directly (see "NATS event system" (`events.md`)) instead of calling anything. Sample implementation for the two invoked contracts, with **two** independent tools per phase to demonstrate that a phase may hold more than one step: `platform_servers_test.go`'s in-process `authorization-mcp-server` stand-in (`call-authorization`/`result-authorization` reject only names/results containing `"bad"`; `call-authorization-role-check`/`result-authorization-length-check` reject role `"guest"`/results over a length limit) — every one of its tools is marked as a triggered tool via `Meta`, but nothing stops a server from marking only some.

- **Native (in-process) triggered tools**: a triggered tool doesn't have to be a discovered backend at all. `proxy_utility.request_constraints_validation`/`proxy_utility.result_constraints_validation` (`constraints_validation.go`) are plain Go functions matching `NativeCallAuthorizationFunc`/`NativeResultAuthorizationFunc` (`triggered-tools-runtime/native.go`), registered on `Runtime` at startup via `Runtime.RegisterNativeCallAuthorization`/`RegisterNativeResultAuthorization` (`main.go`'s `doRunOn`, right after `NewRuntime`) rather than `mcp.AddTool`. This exists because the two mechanisms above don't compose for a native `proxy_utility.*` tool: the discovery-only `isHiddenTool` hiding (`dynamic_proxy.Gateway.registerTool`) never runs for a tool added directly via `mcp.AddTool(gateway.Server(), ...)`, and `Runtime.session`'s dial-a-discovered-backend invocation path can't reach an in-process tool at all (`"proxy_utility"` is a reserved server name `OnAdded` refuses, and even if it weren't, a loopback HTTP call from inside an orchestration step has no credential to attach — an orchestration step passes caller identity as explicit `CallAuthorizationInput`/`ResultAuthorizationInput` struct fields, not headers). So these two tools are never registered as real `*mcp.Tool` objects at all — hidden from `tools/list` by omission, not by hide-after-register — and `orchestrate.go`'s `invokeCallAuthorization`/`invokeResultAuthorization` check `step.Server == dynamic_proxy.UtilityServerName` before falling back to `r.session(...)`+`sess.CallTool(...)`, dispatching to the registered native function directly: no MCP wire format, no HTTP, no auth question to answer. `validate.go`'s lazy signature validation is skipped for a native step for the same reason it's safe to skip: there's no remote schema to drift from, the Go function signature *is* the contract, enforced by the compiler. `request_constraints_validation`/`result_constraints_validation` reach `declarative-guardrail`'s `evaluate_declarations` tool (an ordinary, non-triggered, discovered backend — see "Declarative constraint validation" (`guardrails.md`)) through `Runtime.SessionFor`, an exported wrapper around the same cached-session mechanism `Runtime` already uses for a discovered triggered-tool step's own `(server, tool)` name.

- **A discovered triggered tool can relay back through the proxy, exactly like an ordinary backend call.** `Runtime.session`'s `platformHTTPClientFor(serverName)` (`runtime.go`) uses the same `relayheaders.ServerTransport` as `session_proxies.go`'s `backendHTTPClientFor`: per request, it attaches the headers the calling `ctx`'s minter produces for that platform server — the identity assertion always, and a relay token plus callback URL if `internalAuth.relay` lets that server relay (see "Internal identity assertions" (`auth.md`)). This works with no new plumbing because `Guard`'s own `ctx` (`orchestrate.go`) already carries the minter by the time it reaches `session`/`SessionFor` — `createMiddleware` puts it there upstream of ever dispatching to `Guard`. Concretely, this means a discovered triggered tool's own incoming request (`req.GetExtra().Header`) carries the same `X-Go-Proxy-*` headers a directly-called backend tool on the same server already sees, so it can call `relayheaders.Extract`/dial the callback URL/relay a call back through the proxy exactly as that server's own ordinary tools do — see "Business logic validation" (`guardrails.md`) for the concrete payoff (`validate_store_requests` calling `fetchActiveDeals`/`fetchCustomerType` unchanged, the same functions `purchase_products` itself uses). A **native** step still has no header round trip at all (it's a direct Go function call, never touches `platformHTTPClient`) — this capability is specific to discovered triggered tools. Test: `triggered-tools-runtime/runtime_test.go`'s `TestSessionAttachesRelayHeadersFromContext` proves the header attachment directly; `platform_servers_test.go`'s `validate_budget_tool` stand-in (Scenarios 11-12) proves a full relay round trip through a real, running proxy.
- **Config**: an optional `governanceOrchestration` combined-config section (`config.go`'s `proxyConfigFile.Orchestration` — only the file's outer JSON key is `governanceOrchestration`; `triggered-tools-runtime/config.go`'s `OrchestrationConfig`, parsed the same `ParseConfig(data []byte)` way as `discovery`/`accessRules`, and every other place this feature is called "orchestration" — the `configsync` section name used for the `orchestration-override` ConfigMap, and the `_admin.update_orchestration`/`export_orchestration` admin tools, which exchange `OrchestrationConfig` directly with no outer wrapper key) — named `Orchestration`s, each with three **separate, explicitly-typed step lists**: `callAuthorization`, `resultAuthorization` (each `[]OrchestrationStep{Server, Tool, Parameters}` — no per-step `"type"` field; which contract a step must implement is implicit from which list it's in), and `toolCallAudit` (`[]string`, a closed, independent set of 0–2 recognized sentinel values, each a publish-or-not switch for a distinct event type, no duplicates — `ToolCallAuditSentinel` (`"publish-tool-request-result"`) and `ToolRequestAuditSentinel` (`"publish-tool-request"`); `validateToolCallAudit` in `config.go` enforces all of this at parse time, both, either alone, or neither are valid). This structure is deliberate: the order *between* phases is fixed and not configurable (see `Runtime.Guard` below), but each authorization phase can hold more than one step, and order *within* a phase's own list is significant — a flat, interleaved `steps` array would misleadingly suggest cross-phase order is configurable when it isn't. Plus `toolMappings` (namespaced-tool-name glob pattern → orchestration name, first match wins, via `access_control.GlobMatch`). Absent section ⇒ `triggered_tools_runtime.NewRuntime(nil)` is a total no-op — every call proceeds unguarded, matching pre-orchestration behavior exactly. See `proxyserver/testdata/orchestration_test.cfg` for a worked example.
- **Per-step execution parameters**: `OrchestrationStep.Parameters` is an optional execution parameters string an orchestration author attaches to a specific `callAuthorization`/`resultAuthorization` step — a plain string (not an embedded JSON value) so the step's own shape stays simple, but its *contents*, if set, must decode as a JSON object, not just any valid JSON (a syntactically-valid scalar or array is exactly as unusable to a consumer expecting named fields): `config.go`'s `validate()` (via `validateStepParameters`) checks this once at orchestration-parse time — `json.Unmarshal` into a `map[string]any`, not merely `json.Valid` — failing closed rather than letting a malformed-or-wrong-shaped value surface later as a silently-logged warning inside whichever triggered tool tries to decode it. It's threaded through verbatim, unmodified, as `CallAuthorizationInput.Parameters`/`ResultAuthorizationInput.Parameters` (`contract.go`) by `orchestrate.go`'s `invokeCallAuthorization`/`invokeResultAuthorization` — a triggered tool decodes whichever fields it expects out of it (or ignores it entirely); an empty string means the step configured none. The `authorization-mcp-server` stand-in's `call-authorization-role-check`/`result-authorization-length-check` tools demonstrate consuming it (`logParameters`, decoding into a JSON object and logging each field — its own decode-error branch is defensive, unreachable in practice since config validation already guarantees the object shape) — purely illustrative, it doesn't change either tool's authorization decision. See `proxyserver/testdata/orchestration_test.cfg`'s `"parameters"` entries on those same two steps for a worked example.
- **Hiding is tool-level, enforced at registration time, not a discovery-time split**: every discovered server — regardless of whether any of its tools are triggered tools — goes through the exact same path: both `gateway.OnAdded`/`OnRemoved` (`dynamic_proxy.Gateway`, the client-facing registry) and `triggeredRuntime.OnAdded`/`OnRemoved` (`triggered_tools_runtime.Runtime`, which just records connection info for later `CallTool`-by-name use) receive the identical, unfiltered `discover_mcp_servers.ServerMap` from `main.go`'s `ServerMonitor` callbacks. Visibility is decided per-tool, inside `dynamic_proxy.Gateway.registerTool` (`gateway.go`), via an injected `ToolVisibilityFilter` predicate — `NewGateway`'s `isHiddenTool` parameter, wired in `main.go` to `triggered_tools_runtime.IsTriggeredTool` directly. `dynamic_proxy` cannot import `triggered_tools_runtime` itself (the reverse import, for `ReservedServerName`, already exists — this would cycle), hence the injected-predicate indirection rather than a direct call. When `isHiddenTool(tool)` is true, `registerTool` skips `mcp.AddTool` entirely and defensively calls `RemoveTools` on that namespaced name (covering the case where the tool was visible on a prior poll tick and has since been marked hidden) — this makes a tool's triggered/non-triggered status fully dynamic, re-evaluated on every poll tick, no restart required,.
- **`triggered_tools_runtime.Runtime`** (`runtime.go`) is the `AccessPolicyEngine` structural analog: mutex-guarded `*OrchestrationConfig` + a lazily-dialed, cached session per server that hosts a referenced triggered tool, in a `sessioncache.Cache` (the same cache, connect pattern and `DisableKeepAlives` rationale as `session_proxies.go`; see `gateway.md`: the connect runs outside any lock with its own timeout, so one hung platform server doesn't stall rate-limit checks or guardrail steps for the others), plus an optional, mutex-guarded `EventPublisher` (see `event_publisher.go`, installed via `Runtime.SetEventPublisher` — a post-construction setter, not a `NewRuntime` parameter, so existing `NewRuntime(cfg)` call sites are unaffected). `Update`/`Snapshot` mirror `AccessPolicyEngine.Update`/`Snapshot`'s whole-config-replace semantics. Deliberately **not** built on `dynamic_proxy.genericRegistry`/`FeaturePoller` — a triggered tool is invoked by a fixed, config-declared `(server, tool)` name, so there's no live registry to maintain, just a one-shot `ListTools` (for validation) and direct `CallTool` by name.
- **Lazy signature validation** (`validate.go`): the first time an orchestration is actually used, every step in its `callAuthorization`/`resultAuthorization` phase lists is `ListTools`'d and its `InputSchema`'s property-*name* set (not deep type/required equality) is compared against what that phase's contract expects — derived from `contract.go`'s Go structs via `jsonschema.For[T]`, never hand-maintained, so the expected set can't drift from the actual contract types. `toolCallAudit` has nothing to validate this way — it names no tool, just the sentinel switch, already structurally checked by `config.go`'s `ParseConfig`. A validation failure fails closed, exactly like a call-authorization rejection.
  - **Only definitive results are cached**, per orchestration name: valid, or a step whose tool is missing or has the wrong schema. `Update` clears the cache (a config change may reassign servers/tools; an epoch counter keeps a check started under the old config from being cached under the new one). A check that couldn't complete — a step's server undiscovered or unreachable, its tool list unavailable (`transientValidationError`) — fails that call closed and isn't cached, so the next call checks again. Caching it would let a blip, or a caller cancelling the very first call, refuse every call to that orchestration until the next restart.
  - **One check per orchestration at a time, on its own context.** Concurrent first calls share one check (`Runtime.validating`), run on `context.WithoutCancel` of the first caller's context (its values, so the `ListTools` calls carry that caller's identity like the call itself would) bounded by `validationTimeout` (15s). Each caller waits only as long as its own context. No lock is held during the check's network calls.
  - Tests: `validate_test.go`'s `TestValidationNotSpoiledByCancelledCaller`, `TestValidationRetriesUnreachableServer`, `TestValidationCachesSchemaProblem`.
- **A tool mapped to an orchestration that doesn't exist is refused, not run unguarded.** `ParseConfig` (`config.go`) rejects a `toolMappings` entry naming an unknown orchestration, at startup and on `_admin.update_orchestration` (see `configsync.md`). As a backstop, `MatchOrchestration` still counts such a mapping as a match, and `Guard` rejects the call ("orchestration X not found") when the name isn't in its current config snapshot — which also covers an update removing the orchestration between `MatchOrchestration` and `Guard`. Test: `orchestrate_test.go`'s `TestMissingOrchestrationFailsClosed`.
- **`Runtime.Guard`** (`orchestrate.go`) is the phase-based engine `middleware.go`'s `createMiddleware` calls for any `*mcp.CallToolRequest` matched by `Runtime.MatchOrchestration` (checked right after the existing `isToolRoleAuthorized` check): all of `orch.CallAuthorization`'s steps, in list order (short-circuit/fail-closed on first reject or tool-invocation error) → **the `tool-request` publish switch** (`fireRequestAudit`, gated on `ToolRequestAuditSentinel`), fired the instant call-authorization's verdict is known — rejected or not — and always before the real call is attempted → the real backend call (implicit — `Guard`'s `doCall` callback, which is just `next(ctx, method, req)`) → all of `orch.ResultAuthorization`'s steps, in list order (same short-circuit/fail-closed) → **the `tool-request-result` publish switch** (`fireAudit`, gated on `ToolCallAuditSentinel`), fired via one detached goroutine (`context.WithoutCancel` + a timeout, so it outlives the returning HTTP handler), **unconditionally, exactly once**, regardless of which phase (if any) rejected. The two switches are independent — `orch.ToolCallAudit` may hold either sentinel alone, both, or neither, checked via `slices.Contains` (not "is the slice non-empty", since it may hold more than one distinct value); each switch's own injected publisher (`EventPublisher`/`RequestEventPublisher`, installed via `SetEventPublisher`/`SetRequestEventPublisher`) being nil just logs a warning and drops that event, the same nil-safe-optional-capability convention used throughout this codebase. A misconfigured-orchestration failure (`ensureValidated`) fires only the `tool-request-result` switch, never `tool-request` — call-authorization never actually ran to produce a verdict for it to report. A rejection surfaces to the client as a Go error, mirroring the existing `isToolRoleAuthorized` deny convention (not a "clean" `CallToolResult{IsError:true}`). `tool-request-result`'s `Subtype` alone encodes the outcome (`result-blocked`/`call-failed`/`call-succeeded` — see `ToolRequestResultEvent`'s constants) rather than a separate authorized bool; `CallResult` is `nil`/absent when call-authorization rejected before any backend call was made or the call itself failed, and populated (even when result-authorization itself rejected) otherwise. `tool-request`'s own `ToolRequestEvent` has no `CallResult` field at all — it always fires before any call is attempted, so there's never a result to carry; its `Subtype` is one of just two values (`ToolRequestBlocked`/`ToolRequestOK`, see `event_publisher.go`).
- **`_admin.update_orchestration`/`_admin.export_orchestration`** (`admin_tools.go`'s `registerSectionAdminTools`) mirror `_admin.update_role_permissions`/`_admin.export_role_permissions` exactly — both are table-driven instantiations of the same generic helper, with the same `configsync`-backed cross-replica ConfigMap sync (see "Configuration sync (configsync)" (`configsync.md`)). Note updating an orchestration only changes *which* orchestration a tool-name pattern maps to — it has no bearing on which tools are hidden, since that's purely a property of each tool's own `_meta`, set by the backend server itself.
- **`runProxyServer`/`doRun` are thin wrappers** around `runProxyServerOn`/`doRunOn` (both take an explicit listen `addr`, default `:8081` from the wrapper); `runProxyServerOn` returns a bind failure as an error rather than calling `log.Fatal`. This lets `platform_servers_test.go` run a second proxy instance on a different port in the same test binary as `integration_test.go`'s `TestProxyClient` (which binds `:8081`) without a bind failure taking down the whole `go test ./...` process via `os.Exit`.
- `CallAuthorizationInput.CallRequest`/`ResultAuthorizationInput.CallResult` are declared `any`, not `json.RawMessage`: `jsonschema-go` infers `json.RawMessage` (a `[]byte`) as an "array" schema, which then rejects any real request/result JSON object at validation time. `any` infers to an unconstrained schema and still marshals correctly when the runtime assigns a `json.RawMessage` value into the field (it implements `json.Marshaler`). `ToolRequestResultEvent.CallRequest`/`CallResult` (`event_publisher.go`) are `any` for the same reason, even though nothing schema-validates them — consistency with the two invoked contracts' fields.
